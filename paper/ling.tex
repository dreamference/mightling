\begin{abstract}
Terminal coding agents such as the Codex CLI are open source, but they are built around a
hosted model, a vendor account and a cloud of companion services. We describe \emph{Mightling}, a
coding agent whose model runs on one NVIDIA GB10 workstation (128\,GB of CPU--GPU unified memory):
a 27B-parameter model (Qwen3.8-27B, NVFP4) served locally through SGLang with a block-diffusion
drafter. Source code, prompts and inference never leave the machine, and no vendor account is
involved. Mightling is a fork of the Codex CLI (release \code{rust-v0.158.0}, 4{,}894 Rust source
files, 1.93 million lines). Its central engineering choice is to keep the fork almost identical to
upstream. The upstream tree is never edited. Each build exports it, applies a series of 23 patches
totalling 43.0\,KB (43 files, $+170/-53$ lines), and links in a separate crate that does the actual
work of localisation: model discovery, configuration, prompt rebranding, help-text rewriting, a
signed release-based updater and refusal of cloud-bound commands. The localisation itself takes
about 9\,KB of the series; every feature beyond it costs one hook in Codex and puts its logic in a
crate of ours. We describe the inventory of the cloud dependencies that are switched off, the
trace-based audit that keeps them off, an enforced network switch, the integration points between a
vendor harness and a local model that are not visible from the documentation, and the host-safety
layer that unified memory requires. On a 100-task sample of SWE-bench Verified, run inside each
task's container on this machine, the agent resolves 68; calibrated against the 175 published
leaderboard submissions on the same tasks, that corresponds to about 69\% on all of Verified
(95\% band 64--73\%). A two-session ``study, then fix'' mode resolves 69 of the same 100 at 2.2
times the time, and four prompt and harness changes measured as paired A/B nights on fresh tasks
show no measurable difference; three runs of one configuration on the same 44 tasks resolve 29, 29
and 31, and some run resolves 36. The fork also carries, each from the same launcher crate or
beside it: a terse-answer mode that halves answers to questions and leaves coding work unchanged, a
compaction limit tied to the server's KV pool with a rule-built ledger of what summaries lose, a
two-layer code index (a tree-sitter knowledge graph plus compiler-exact SCIP data), an overnight
task queue that works in git worktrees, and a client/node split that pairs workstations over SSH.
We are explicit about what is estimated rather than measured.
\end{abstract}

\section{Introduction}

Agentic coding tools now read repositories, run shell commands and edit files autonomously
\cite{yao2023react,yang2024sweagent,wang2024openhands}. The most capable are open-source clients of
proprietary services: the client is inspectable, but a session sends source code, prompts and tool
output to a hosted model, which regulated industries, security research and anyone whose code is
the asset cannot accept. Two developments make a local alternative plausible: open-weight models
quantised to four bits \cite{cheng2023autoround} with speculative decoding
\cite{leviathan2023speculative,chen2026dflash} generate at interactive speed on one desk-side
machine, and the leading agent clients are open source, so a local deployment can reuse their
tool-calling loop, sandboxing, approval flows and terminal UI. Reusing a fast-moving upstream has a
cost: a fork that edits freely soon cannot take upstream releases, and one that edits nothing
cannot remove the parts that assume a cloud. This paper describes how Mightling, a local AI stack
for the NVIDIA GB10 made by Dreamference, resolves that tension in its terminal coding agent.

\paragraph{What ``local'' means here.} The model, the agent and all session state run on one
workstation; source code, prompts, tool output and model traffic never leave it, and a traced
session shows no connection to any vendor (\cref{sec:egress}). Mightling is not air-gapped: web
search goes through a SearXNG \cite{searxng} instance on the machine, mail is read over IMAP,
\code{ling update} contacts GitHub, and the phone messengers reach their networks once turned on.
Each can be switched off, and \code{/airgapped on} gives every command the agent runs an empty
network namespace.

\paragraph{Contributions.} A \textbf{patch-minimal fork method} for a large Rust agent
(\cref{sec:fork}): an unmodified pinned submodule, a build-time export, one- and two-line hooks,
and an external crate linked into the binary, with the four techniques that keep the series at
43.0\,KB, of which the localisation is about 9\,KB. An \textbf{inventory of the cloud surface} of a
coding-agent client and its treatment (\cref{sec:cloud}), a trace-based audit that re-checks it
after every build, and a network switch enforced in the command sandbox. \textbf{Integration
points} between a vendor harness and a local model (\cref{sec:local}): model discovery, a
compaction limit the server's memory sets, and tool types the server silently drops. A
\textbf{host-safety layer for unified memory} (\cref{sec:safety}). A \textbf{measured cost model}
for a local agent's output and the terse-answer mode built on it (\cref{sec:local}). A
\textbf{task-level evaluation on SWE-bench Verified} on an arm64 desk machine (\cref{sec:swebench})
with a calibrated overall estimate, a classification of every failure, and paired A/B nights that
measure what one night can detect. A code index (\cref{sec:index}), an overnight task queue
(\cref{sec:night}), workstation pairing (\cref{sec:node}) and the design principles behind them
(\cref{sec:lessons}).

\section{Background}

\paragraph{The Codex CLI.} The Codex CLI \cite{openai2026codex} is an open-source Rust workspace of
about 160 crates: a terminal UI, a non-interactive \code{exec} mode, session resume and fork, a
platform sandbox (Bubblewrap on Linux) and an approval model for tool calls. In \emph{Code Mode}
the model is given a single \code{exec} tool and writes short JavaScript programs, run by a
separate V8 host process (\code{codex-code-mode-host}), within which every other tool, including
Model Context Protocol (MCP) \cite{mcp2025spec} tools, is a function. Codex talks to open-source
providers (\code{-{}-oss}) through a chat-completions endpoint, but login, cloud tasks, connectors,
usage limits and feedback upload assume an account with the vendor's hosted service.

\paragraph{The machine.} The NVIDIA GB10 pairs an Arm CPU with a Blackwell GPU (compute capability
12.1) over 128\,GB of shared LPDDR5X. No memory is reserved for the GPU: model weights, KV cache,
the desktop and every other process draw from one pool, which shapes \cref{sec:safety}.

\paragraph{The model.} Qwen3.8-27B in an NVFP4 checkpoint, served by SGLang with a calibrated NVFP4
DFlash2 block-diffusion drafter \cite{chen2026dflash,dflash2drafter} proposing twelve tokens per
step (7\% faster than sixteen on replayed sessions; eight, ten and fourteen gain nothing), a
262k-token context, about 38\,GB free while serving. Single-stream it decodes 32.0, 68.6 and 84.1
tokens/s on prose, code and JSON; replayed agent sessions decode about 48 tokens/s at a step of
about 103\,ms with 5.2 tokens accepted per step, and 33.9 tokens/s each on two streams. The server
manager also drives vLLM \cite{kwon2023vllm}, so the method does not depend on one engine.

\section{A patch-minimal fork}
\label{sec:fork}

\subsection{Build pipeline}

Codex is vendored as a git submodule of our own GitHub fork, pinned to the stable release tag
\code{rust-v0.158.0}, and \emph{never modified}: the builder's tests assert that \code{git status}
inside it is empty after a build. A build exports the pinned \code{codex-rs/} with
\code{git archive}, copies the launcher crate in as \code{codex-rs/ling}, applies the series with
\code{git apply -{}-check} before \code{git apply} so a stale patch fails before anything is
half-applied, builds \code{ling} and \code{codex-code-mode-host} with Cargo, installs them side by
side, and records a build key (submodule commit, patch bytes, launcher sources) so an unchanged key
skips the build. Moving to a new upstream release means bumping the submodule and resolving
whichever hunks stop applying; because the hunks are few and small, conflicts are local and
obvious.

\subsection{Four techniques keep the series small}

\Cref{tab:patches} shows the series. \emph{Rename at run time, not in the tree}: renaming the agent
inside Codex's bundled model catalogue would cost about 395\,KB of diff, since each 20\,KB
system-prompt template is one JSON line; the launcher instead reads the catalogue through the
upstream crate's public function, replaces the identity sentence, and hands the result to Codex in
the catalogue it writes anyway. \emph{Rewrite presentation where it is assembled}: one hook routes
argument parsing through a launcher function that walks the \code{clap} tree once and rewrites the
product name in every \code{about}, \code{help} and \code{bin\_name}. \emph{Use the build system's
own unification}: one \code{openssl-sys = \{features = ["vendored"]\}} line in \emph{our} manifest
applies to every crate that links OpenSSL, and a path dependency inside the workspace root makes
the launcher a workspace member without editing the workspace manifest. \emph{One line per
behaviour}: what remains is a \code{false} from a visibility predicate, a \code{hide = true}, or a
dispatch arm sent into the launcher.

\paragraph{A feature costs a hook, not a diff.} Patches 0001 to 0016, the localisation, are about
9\,KB of removals and redirections. From 0017 on the patches are features, each with its logic in a
crate of ours and only its entry point in Codex: \code{/cavemode} and \code{/night} add a
slash-command variant and its dispatch arm (566 and 769 lines in the launcher with their tests);
\code{/airgapped} is one call in each place a command's permissions are resolved; flattening MCP
tools and observation masking each route one step of request assembly through a crate of ours;
\code{/apps} answers Codex's connector list from the launcher; \code{/node} suspends the TUI so a
password typed there never enters the session. A test caps the series at 43{,}000 bytes, raised
only explicitly in the commit that needs it. Two build details need no patch: Code Mode's V8
flavour is not published for \code{aarch64-unknown-linux-gnu}, so the builder fetches upstream's
own prebuilt archive and verifies it against the submodule's digest manifest \cite{rustyv8}, and two
release-profile overrides take the binary from 1.4\,GB to 315\,MB.

\section{Cutting the cloud cord}
\label{sec:cloud}

Every subcommand and slash command of Codex 0.158.0 was audited for a dependency on vendor-hosted
services; \cref{tab:cloud} lists the result under four treatments. \emph{Refuse}: the launcher
rejects the command before Codex parses it. \emph{Hide}: the command leaves help and menus but stays
compiled for a future private-cloud implementation. \emph{Replace}: the same command does something
local. \emph{Remove}: the command is unreachable. Hiding alone is not a security boundary, since a
hidden clap subcommand still parses, so the commands that start a vendor sign-in or browse the
vendor's servers are also refused, by a check that reads Codex's own clap definitions and so
refuses \code{ling -c k=v cloud} as well.

\subsection{Traffic an audit of commands does not find}
\label{sec:egress}

Auditing commands finds the channels a user starts deliberately and none of those Codex opens by
itself. Those are found by tracing real sessions under \code{strace -f -e trace=connect,execve} with
the HTTP client's debug logging on; with the model on loopback, anything else in the trace is
unintended. An upstream build with no vendor login opens four channels: OpenTelemetry metrics to
Statsig at \code{ab.chatgpt.com}, the default in release builds, with an API key compiled in; a
\code{git ls-remote} of the vendor's plugin repository; a request for featured plugins to
\code{chatgpt.com}; and an announcement fetch from \code{raw.githubusercontent.com} on every
interactive start. Two more open whenever a login is present in the shared
\code{\textasciitilde/.codex}: usage analytics and token refresh. Each is closed where it originates,
so no setting or later login can reopen it; Mightling keeps its state in
\code{\textasciitilde/.mightling}, never the login; and the launcher points Codex's
\code{chatgpt\_base\_url} at a closed local port, so any vendor-backend call we did not find fails on
the machine. What a vendor client sends is an empirical question, re-measured after every upstream
update.

\paragraph{The audit as a command.} That trace is \code{ling-admin audit egress}, run by every
build after installing a new binary: one real session in a throwaway repository and home under
\code{strace -f -e trace=connect,sendto,sendmsg,sendmmsg,execve}, passing only if every destination
is an allowlisted loopback port, no DNS query was sent and no git command reached a network; a
trace that itself failed is never a pass. glibc sends name lookups with \code{sendmmsg}, so tracing
\code{connect} alone misses a query, and a connection to the stub resolver at \code{127.0.0.53:53}
is loopback yet still a query that leaves the machine. A messenger bridge talks to its network
outside the agent's process, so every report names each bridge that is on as a declared exception.

\paragraph{An enforced network switch.} At \code{/airgapped on}, every command the agent runs gets
an empty network namespace. The hook is in Codex's sandbox helper, not its core: core derives a
command's network policy in about a dozen places, while every sandboxed command passes through the
helper. The level resolves from the session, then an environment variable, then the stricter of the
repository's and the user's configuration, because the agent can write the former. Full Access has
no sandbox, so the launcher, the permission menus and the app server each refuse the combination.

\paragraph{Updates.} \code{ling update} downloads the latest published release's binaries with a
SHA-256 manifest, verifies both before replacing either, and swaps them in next to the running
executable. Releases are \emph{signed}: the checksum file carries an Ed25519 signature made in a
protected CI environment, the public key is compiled into \code{ling}, and the updater and the
installer refuse a release whose signature is missing or does not verify; the key is usable only
from the main and release branches.

\section{Running a vendor agent against a local model}
\label{sec:local}

\paragraph{Discover, do not configure.} The server's \code{/v1/models} reports the served model and
its \code{max\_model\_len}, and the launcher derives the catalogue entry from it rather than
recording which model is served. Codex parses catalogue entries with strict \code{serde} structs,
and \code{base\_instructions} is the \emph{entire} system prompt: with a placeholder there the model
has no description of its tools and falls back to \code{curl}, so the launcher supplies Codex's own
template with the identity sentence rebranded. Codex's \code{config.toml} accumulates tables Codex
itself writes, so the launcher edits it as a syntax tree rather than appending keys that silently
join the last table.

\paragraph{The compaction limit follows the server, not the model.} The model reports a
262{,}144-token context, but the server's KV-cache pool, sized at launch from free memory and shared
by every stream, holds about 157{,}000 tokens, so a compaction limit derived from the window would
exceed what the server can hold; and a compaction is expensive, since the model re-runs what the
summary dropped (at an extreme limit of 6{,}000, one small task compacted seven times and ran
thirteen commands where three were needed). Two mechanisms follow, neither a patch. The launcher
reads the pool from the server's metrics at every start and passes 60\% of it as the compaction
limit unless the user set one (94{,}144 tokens here). And a ledger replaces what summaries lose:
Codex's summary keeps the prose but drops every tool call and output, so a hook run after each
compaction has the launcher rebuild by rule, with no model, in about 15\,ms, the files the session
touched, the commands that failed since the last compaction and the last test result, and hand them
back as context. On one long task at a 32k limit, the session with the ledger compacted 11 times
instead of 24 and ran 114 commands instead of 245; after a compaction only 1\% of commands repeat an
earlier one exactly. Benchmark sessions, at a 49{,}152-token limit, compact far more: across seven
runs of 320 tasks, tasks that compacted at most once resolved 75--78\%, twice 57\%, and three times
or more 38\% (50\% against 40\% on the 18 tasks that ran both ways), and compaction took 17\% of
all agent time at a median of 98\,s. Compacting at the end of a turn instead of mid-turn is built
as a setting and off until a benchmark of interactive sessions decides it.

\paragraph{Tools as shell commands, and tool types at the boundary.} The agent's primary tools are
shell commands described in the system prompt (\code{ling-search}, \code{ling-fetch},
\code{ling-code}, \code{gmail}), which a local model calls reliably and which need no tool type the
server has to understand. Codex sends two kinds of tool a local server drops: MCP tools go out in a
\code{namespace} tool type of Codex's own, and Code Mode's \code{exec} and the free-form
\code{apply\_patch} go out as \emph{custom} tools whose argument is raw text under a grammar. Both
SGLang and vLLM drop tools of a type they do not know, so none of them reaches the model as sent.
Patch 0020 sends each MCP tool as a plain function; on a server other than our own engine, the
launcher's tool crate offers \code{exec} as a function with one string parameter, the grammar in
its description, turns the model's call back into the custom-tool call Codex expects before Codex
records it, and replays earlier calls in the form the model saw. With that, the model calls
\code{exec} in every one of 44 benchmark tasks, 2{,}865 times; the \code{apply\_patch}-as-function
arm never started, because the pinned Codex's catalogue parser accepts only the free-form variant
(\cref{sec:swebench}). The request that reaches the model, not the one the harness builds, is the
thing to inspect. Codex's only pre-token timer, a 300\,s stream-idle timeout, covers the server's
queue as well, which several queued streams exceed, so the launcher writes 900\,s unless the user
set one.

\paragraph{Prose is the expensive output.} Locally the currency is time, and its exchange rate is
lopsided: this model decodes prose at 25--32 tokens/s and reads a prompt at about 1{,}700, so one
token of prose costs the time of about 50--70 prompt tokens, and 81\% of recorded input comes from
the prefix cache. Standing instructions are nearly free; every sentence of answer is not. Across 52
recorded sessions, 75.5\% of output tokens are tool-call arguments, 23.1\% final answers and 1.3\%
commentary. Mightling therefore answers tersely by default. A \emph{cave mode} level (\code{off},
\code{lite}, \code{full}, \code{ultra}; \code{/cavemode} switches it) is a section of model-visible
session state the launcher contributes through Codex's extension registry, the level's text once
and a one-line reminder each later turn; the system prompt is untouched, so \code{off} is exactly
upstream. In 532 single-turn runs and 11 sessions of eight or nine turns, the default \code{ultra}
(at most three sentences of prose outside code unless asked) cut answers to questions to 0.42--0.57
of their length at \code{off} and wall time to 0.41--0.74, passed 35 of 36 correctness checks, the
same as \code{off}, and moved nothing on coding tasks, as a paired study of the public ``caveman''
skill found on a hosted agent \cite{shiryaev2026caveman}. Content rules (answer first, one option, no unrequested code, a numeric sentence cap) work where
adjectives such as ``short'' barely do, and a level fades unless repeated: with the per-turn
reminder, turns five to eight sum to 0.49 of \code{off}. Only what the model writes is compressed,
since compressing what it reads makes models answer longer and worse \cite{adeyemi2026cavewoman}.
Email, a prompt-injection channel for an agent holding a shell, is read-only, framed between
\emph{BEGIN EMAIL (untrusted)} and \emph{END EMAIL} markers, and declared never to be instructions;
a mitigation, not a defence.

\section{Host safety on unified memory}
\label{sec:safety}

With no dedicated GPU memory, a model load competes with the desktop for every page. A load that
outruns reclaim takes the workstation down hard enough to need the power button, without invoking
the kernel OOM killer: driver-pinned pages are unreclaimable and charged to no process the killer
would select, so the kernel spins in direct reclaim. The server manager enforces two layers.
\emph{Admission checks before a load}, reported together because each fix needs its own
\code{sudo}: an OOM handler (systemd-oomd or earlyoom) acting on pressure-stall information
\cite{linuxpsi}; at least 64\,GB of swap; \code{vm.min\_free\_kbytes} at 1\,GiB or more, since the
stock 44\,MB is exhausted between reclaim passes by a loader reading gigabytes per second;
\code{vm.watermark\_scale\_factor} at 200 or more; and sysstat, whose history is the only pressure
record that survives a hard reset. The container is the preferred OOM victim
(\code{oom\_score\_adj}\,=\,800), and \code{ling-admin host setup} applies what the checks report,
with an AppArmor profile that lets Bubblewrap create the sandbox's user namespace. \emph{A watchdog
during a load} samples \code{/proc/pressure/memory} once per second and kills the container when
the ``full'' stall share over 10\,s stays at or above 60\% for 5\,s (systemd-oomd's default) or the
60\,s average reaches 25\%, which catches pressure that oscillates around the first threshold. The
kill tries three paths in the order the host can still afford: a direct \code{SIGKILL} to the
cgroup, one request over Docker's Unix socket with no fork, and the Docker CLI last, because
forking a Go binary is the work least likely to be scheduled during a reclaim livelock. The margins
decide the context a model can run at, and anything resident beside the server starts before it
with a fixed cgroup cap, because the server's pre-flight reads current free memory. Every heavy
background job runs under \code{systemd-run -p MemoryMax=\ldots{} -p MemorySwapMax=0}, so
exhaustion kills the job, not the host; index runs share one slice and one memory ledger, each
overnight task has a scope of its own, and while a night run holds its lock a model load, a build
and a re-index all refuse to start.

\section{Task-level accuracy on SWE-bench Verified}
\label{sec:swebench}

\paragraph{Running it on a desk machine.} \code{ling-admin swe-bench} runs \code{ling} inside each
instance's container on the GB10 and grades the patches with the official harness
\cite{jimenez2024swebench}. The official images are \code{linux/amd64} only; the arm64 images are a
community build covering 400 of the 500 instances \cite{swebencharm64}, and an instance is used only
once its gold patch resolves and a no-op patch does not, both checked here. The installed
\code{ling} is relinked against the host's loader for the images' older glibc. Codex's sandbox
cannot start inside a container, so the container is the sandbox, on an internal network that
reaches the model server and nothing else. The server sits behind a streaming proxy, the
\emph{model gate}: while a run holds it, a request from outside the run's network gets a 503 naming
the run and the time left. Each instance gets a 45-minute limit, 8\,GB of memory and four CPUs; two
run at once; one session, one patch, a single attempt in the leaderboard's sense.

\paragraph{From a local subset to an overall score.} A sample is not average: across the 175
submissions that publish per-instance results \cite{swebenchexperiments}, systems resolve on
average 5.9 points fewer of our 24-task sample than of all 500. Two estimators fitted on those
submissions map a local count to an overall score: a regression of overall on subset score, and a
one-parameter item-response (Rasch) model fitted on the full 175$\times$500 matrix. Back-tested on
the published submissions' own 24-task results, the Rasch estimate has an RMSE of 5.3 points (the
regression 5.1), and the 95\% band is $\pm 1.96$ times that error; on 100 tasks the error falls to
2.4 points, a band of about $\pm 5$.

\paragraph{Results.} On the 100-task sample the default configuration resolves 68, about 69\% on
all of Verified (band 64--73\%). On the 24-task sample six rounds resolve 17, 16, 17, 15, 16 and 15;
the median, 16, corresponds to about 71\% (band 60--81\%) and is what several published systems on
much larger hosted or open models score on exactly those tasks, with overall scores between 66.6\%
and 77.6\%; the best published result on them from a 20B--40B model is 15 with several attempts, 14
as a single attempt, all 2025 models. A \emph{refine} mode runs two sessions, one that studies the
task without changing it and writes a structured description, and a fresh one that fixes it;
paired with the default on the 100 tasks it resolves 69, each mode alone resolving about ten tasks
the other misses ($p = 1.0$), at 2.2 times the time per task (median 16\,min 22\,s against
4\,min 7\,s on the 24-task sample). Refine is opt-in.

\paragraph{Why the 32 failed.} Read against each task's difficulty, the share of the 78 published
submissions scoring 60\% or more that solve it, nineteen of the 32 failures are tasks fewer than
40\% of those systems solve. By category: a second code path or file missed (8), the wrong file
(5), the right place but a wrong detail (5), behaviour the issue did not ask for (5), a fix that
broke other tests (4), the benchmark's test patch blocked by the agent's own test edits (2),
stopped mid-work (2) and out of time (1). None came from an empty patch, a tool or environment
error, or a malformed tool call. In four of the seven failed tasks that at least 75\% of those
systems solve, the source change was in the right place and a test decided the outcome.

\paragraph{What one night can measure.} Changes to the task prompt, the harness and the tools of
\cref{sec:local} are measured as paired A/B nights on tasks outside the 100: two arms on the same 44
or 50 freshly validated tasks, one session per task.

\section{Compiler-exact code navigation}
\label{sec:index}

An agent that navigates with \code{rg} and file reads spends many rounds on a 4{,}894-file
workspace and silently misses calls through traits, generics and re-exports. Under the constraints
of a vendor-free AGPL product (a compatible licence, no network or telemetry, arm64 availability),
\code{ling-code}, a Rust binary beside \code{ling}, combines two layers. The \emph{universal} layer
is codebase-memory-mcp \cite{codebasememorymcp,vogel2026codebasememory}, a single MIT-licensed C
binary with 158 tree-sitter \cite{treesitter} grammars that builds an approximate call graph for
every language; the \emph{exact} layer is SCIP \cite{scip} indexes from compiler front-ends
(\cref{tab:indexers}), converted to SQLite. \code{ling-code} answers \code{def}, \code{refs},
\code{callers}, \code{callees}, \code{impl}, \code{impact}, \code{show}, \code{outline} and
\code{search} by reading both stores directly as SQLite, joins them through a definition's location,
and tags every row \emph{exact} or \emph{heuristic}; the agent's prompt requires verification when
a heuristic row decides a rename, a signature change or a deletion, and a store with an unknown
schema is reported while the other layer answers. This follows LocAgent's graph-guided
localisation \cite{chen2025locagent} and CodeNib's multi-view serving \cite{yu2026codenib},
specialised to one self-contained machine.

\paragraph{Why two layers, and the decisions measurement forced.} At file level, the universal
layer's call edges recall 78\% of what rust-analyzer's SCIP index holds for the upstream workspace
(15{,}660 functions with cross-file references) and 58\% of what scip-python holds for our Python
package, 86\% for functions but 52\% for methods; for a method whose name another class shares it
finds no caller of either, where scip-python resolves each. It is good enough to orient and not good
enough to rename by. The router reads the layers' databases directly, because the universal layer's
CLI spends 6.6\,s per invocation on start-up while the same query takes under 10\,ms. Exact Rust
indexing is admitted, not assumed: \code{rust-analyzer scip} on the upstream workspace takes 691\,s
cold and 569\,s warm under a 22\,GiB cap with a peak of at least 21.3\,GiB, an 8\,GB cap is not
enough, and there is no cheaper mode. A snapshot cannot say what it is missing, so every query asks
git which files changed since each layer's snapshot (39\,ms) and searches those for the name
(3\,ms), marking the hits as heuristic text matches; an edit is never a silent miss. A vendored
upstream would make 97\% of our universal index third-party code, so a submodule is indexed only
when it is the user's own, by two offline tests (same host and owner as the superproject, most
recent commits by its authors), or when the user includes it, a choice recorded in the agent's
home, never in the repository. Queries only read, inside the agent's sandbox; indexing runs outside it under one host-wide memory
budget in a network-less Bubblewrap sandbox. Warm queries on our repository answer in 0.09\,s at the
median and 0.11--0.12\,s at the 95th percentile, and \code{refs} on a TypeScript type in the
upstream schema returns the same 48 files a whole-word search finds, in 40\,ms. Not built or not
measured: search by meaning, \code{impact} used by the model, and the effect of an index run on
decode speed; on SWE-bench the agent does not query the index unprompted.

\section{Unattended overnight work}
\label{sec:night}

\emph{Night Shift} lets the user queue coding tasks during the day (\code{/night add}, optionally
with the test command that decides success) and finds a branch and a report for each in the
morning. The slash command writes a task record and never calls the model; the runner, in
\code{ling-admin} under a systemd user timer, runs each task as \code{ling exec} in a git worktree
of its own, on a branch named after the task, in a transient systemd scope with a memory cap. The
runner, not the agent, commits; nothing is merged, pushed or rebased. A task whose worktree is
unchanged and whose last message announces work is resumed with ``go ahead'', at most twice, then
recorded as stalled; a task the window cuts off keeps its worktree and session for the next night.
The run never starts the model server and gives way to the user: admission requires the server to
be answering, the host-safety checks to pass, memory headroom, no build or index run in progress,
and the server's prompt-token counter unchanged for a period, since a gauge of running requests
sampled every 30\,s misses short requests. Each task is budgeted 49{,}152 tokens, which allows two
or three concurrent tasks. The runner's own test run executes code the model wrote, so it runs in
the agent's command sandbox: it can write in its worktree and \code{/tmp} but not in the user's
checkout, its \code{.git} or the home folder, and at \code{/airgapped on} reaches neither the
internet nor the model server. Live, one task has run end to end (\cref{tab:eval}), an interrupted
task has been resumed on a second night, and two tasks have run in parallel while a third waited
at the memory gate; a stall is covered by tests against a scripted stand-in for the agent.

\section{Several workstations}
\label{sec:node}

A machine that serves the model is a \emph{node}; anything else running \code{ling} is a
\emph{client}, which resolves the model server through fixed tiers: an explicit address, the node it
remembered (found again by its identifier, never by address), and finally a multicast DNS browse.
Every unattended caller of \code{ling} names its server explicitly, because a browse is a multicast
query the egress audit would count as traffic. Inference stays open on the local network, which we
treat as trusted; control goes over SSH, never an open port: \code{ling-admin node add} has the
other node authorise a key for one forced command that refuses everything but its own operations
and pins the node's host key to its identifier. A \emph{job} is a command run on a node as a systemd
user unit with a mandatory memory cap and time limit, inside Bubblewrap with the home folder hidden
and no GPU; its changes come back as a git branch. A paired node serving the same model is an extra
model server for Night Shift and SWE-bench. A DHCP lease moves, so a node is resolved by its
identifier before every connection and refused rather than guessed if it does not answer a browse
within a minute; on the GB10's Wi-Fi chip, NetworkManager's default power saving loses up to about
80\% of multicast DNS queries, so the host check reports it and host setup turns it off.

\paragraph{An engine for one model.} The second machine is dedicated to a single-model inference
engine for Qwen3.8-27B with DFlash2, written in C++ and CUDA and outside this paper's build. Its
rule is exactness: every speed change must leave greedy output byte-identical to non-speculative
decoding. It matches the production server on one stream (a step of about 103\,ms) and is within
2\% on two (33.4 against 33.9 tokens/s per stream). Single-step savings are kept only if
bit-identical and no slower at one stream and at two. Two 16-row tiles per block in the
weight-streaming GEMM were kept: the GEMMs already streamed at 233--244\,GB/s at 1--16 rows, but
at 17--32 rows, the batched verify of two sequences, they had fallen to 110--190\,GB/s, and the
change took the per-stream step period at two streams from 154.2 to 147.5\,ms (32.6 to 34.1
tokens/s per stream). The commit's state replay on a second CUDA stream beside the next draft was
kept: 102.6 to 101.4\,ms on one stream (48.6 to 49.2 tokens/s), 147.8 to 146.3\,ms per-stream
period on two (34.0 to 34.3). A third \code{cp.async} stage in the verify attention was rejected:
the kernel already read at the plain-read rate and the batched step got slower (122.3 to
124.1\,ms). These comparisons are at equal acceptance because the replay now sends a sampling seed;
before it did, each request drew its own acceptance, which puts noise of a few percent on every
earlier figure here, 33.4 against 33.9 included, and a comparison is now reported only when both
runs produce the same tokens in the same number of steps. Decode is bound by reading the weights,
17.6\,GB per step, so the remaining gains are in fewer bytes read per accepted token.

\section{Design principles}
\label{sec:lessons}

\paragraph{Keep the fork boring.} Every behaviour that can live in a linked crate lives there, and
every remaining hook is a single call or predicate. The measure of success is how long an upstream
bump takes: a 43\,KB series of one- and two-line hooks turns an upstream release into an
afternoon's review rather than a merge project.

\paragraph{Presentation diffs are the expensive ones.} A one-word rename inside machine-formatted
data costs hundreds of kilobytes of diff; renaming at run time, or where presentation is assembled,
costs nothing in the series. We expect this to be the common case for rebranded forks.

\paragraph{Local models change the tool contract.} A harness tuned for a frontier hosted model
exposes tools in ways a smaller local model may not use and a local server silently drops, so that
a whole class of tools never reaches the model. It is cheaper to adapt the tool surface, by shell
commands and by translating tool types at the boundary, than to wait for either side to adapt.

\paragraph{Measure the noise before the effect.} The same configuration, run three times on the same
44 tasks, resolves between 29 and 31: 23 tasks every time, 8 never, 13 sometimes. Every candidate
tested so far moves the count by three tasks or fewer, so a single run of each arm can only reject
large effects, and each candidate is first judged by the behaviour it was meant to change. The
instruments need the same care: the engine's replays carried sampled-acceptance noise until they
were seeded, and a benchmark night whose candidate arm died at start still exited 0 until each arm
was made to run one task to its end before the night begins.

\paragraph{Unified memory needs admission control, not just limits.} A container memory cap bounds
the container; it does not decide who dies when the host runs short, nor prevent a reclaim livelock
in which nothing dies. Pre-flight checks, pressure-based watchdogs and caps on every auxiliary job
are all necessary.

\paragraph{Outward-facing automation needs its own kill switch.} Releases publish themselves, so a
release run is started only from a release branch, signs with a key usable only there, and is
checked against the repository's notes before it is dispatched.

\section{Related work}

SWE-agent \cite{yang2024sweagent} and OpenHands \cite{wang2024openhands} study the
agent-computer interface and evaluate on SWE-bench \cite{jimenez2024swebench}; we do not propose a
new agent, but show how to take a vendor's production client, keep it upgradable, and make it
vendor-free and self-contained. LocAgent's code graphs \cite{chen2025locagent}, CodeNib's
multi-view context serving \cite{yu2026codenib} and tree-sitter knowledge graphs served over MCP
\cite{vogel2026codebasememory} inform \cref{sec:index}. On the serving side we rely on vLLM's paged
attention \cite{kwon2023vllm}, speculative decoding \cite{leviathan2023speculative} and
block-diffusion drafting \cite{chen2026dflash}; our contribution there is the host-level safety
unified memory requires, not a serving algorithm.

\section{Limitations}
\label{sec:limits}

The SWE-bench figures come from 24 and 100 tasks on community images, one session per task, mapped
to an overall score by models fitted on published submissions; they are not leaderboard results,
and run-to-run variation is several points. All results come from GB10 workstations with one model
configuration. Agent-session throughput is a replay of recorded sessions, reaching 77\% of the
recorded output lengths, taken before the replay sent a sampling seed, so it carries acceptance
noise of a few percent. Upstream's own suite last ran against an earlier patched tree (20{,}380
tests, 20{,}362 passed; sixteen app-server timeouts unexplained), and the slash-command suite of
\cref{tab:eval} on a 16-patch build; both predate patches 0017 on. The code index has no exact
layer for C and C++ on this architecture, its Java and .NET indexers have run only on small
projects, search by meaning and the cost of an index run on decode speed are unmeasured, and on
SWE-bench the agent does not use the index unprompted. Night Shift has run a handful of tasks, and
a stall has not been provoked live. The advertised context still exceeds the KV pool; what the
server does with a larger prompt is untested. The Signal bridge has run live against one account,
the Matrix and Telegram bridges only against stand-ins.

\section{Conclusion}

Mightling shows that a production coding-agent client can be made vendor-free, with its model on a
single unified-memory workstation, without giving up the ability to take upstream releases. The
localisation itself is about 9\,KB of the 43.0\,KB series; every feature beyond it (a terse-answer
mode, an overnight queue, an enforced network switch, flattened MCP and Code Mode tools, connectors
without a vendor sign-in, workstation pairing) costs a hook in Codex and puts its logic in crates of
ours, with no change to the method. The cloud surface is audited and neutralised explicitly and
re-checked by a trace after every build, and the host is protected by admission checks and a
pressure watchdog. On a 100-task sample of SWE-bench Verified the agent's local result corresponds
to about 69\% overall; neither a study-then-fix mode, nor four prompt and harness changes, nor
Code Mode's \code{exec} measure above the run-to-run noise. The next steps are compaction that
drops old tool output before it summarises, choosing among several attempts where time allows
(overnight), and speed: an engine for this one model, on the second workstation, already matches
the production server, is taking milliseconds off each step with its output bit-identical, and has
to pass production on seeded replays of both.
