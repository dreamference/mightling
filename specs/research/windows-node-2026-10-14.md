# A Mightling node on Windows on Arm: RTX Spark laptops

*Research note, 2026-10-14. The owner's decision of the same day: research and gap analysis only, no code. What a Mightling* node *(the model server, the advertisement, pairing and jobs, beside the agent) would need to run natively on an RTX Spark laptop under Windows 11 on Arm, component by component, with the first measurements for the day a unit arrives. Every statement is one of three kinds and says which: read on the web (source named), read from this repository or the engine's (file named), or an estimate or assumption, marked as such. Nothing here was run on Windows: there is no Windows machine here, and the Surface Laptop Ultra the owner is ordering ships from 2026-10-16.*

## 1. What this adds to the Windows spec, and the question it answers

`specs/DREAMFERENCE_MIGHTLING_WINDOWS_ARM.md` (2026-10-06, Phases 0–2 built 2026-10-07, released as a preview in 1.5.1) covers the Windows **client**: the `ling.exe` build, Codex's elevated sandbox and patch `0024` for `/airgapped on` (§7), the ETW egress audit (§14), `install.ps1` (§16.4), a local engine for a lone laptop (§8: W1, a native `llama-server`; W2, SGLang in WSL, not built), and a Windows watchdog in outline (§9). It names "a Windows *node* for other machines on the LAN" a non-goal, "Phase 6 at the earliest" (§3), and it predates ling-engine. The owner's decisions of 2026-10-07 stand as the record: no WSL, W1 only, Qwen3.8-27B everywhere, unsigned preview builds, Python stays on the node.

This note takes the two things that spec did not: **ling-engine built natively for Windows on Arm as the node's model server**, and **the node half** (advertisement, SSH pairing with a forced command, capped jobs, lanes, the gate). The 2026-10-14 ask poses the native engine as the candidate to assess, not as a reversal of W1: `llama-server` remains the fallback engine the Windows spec chose, and nothing is decided here.

The short answer: **the GPU side is the smaller problem; the operating-system side is the larger one.** The N1X is the GB10 die (ServeTheHome; StorageReview), CUDA 13.4 ships a native Windows Arm64 toolkit, and the engine's own code has one POSIX surface (`mmap` in `safetensors.cpp`) and one vendor library on its way out (cuBLAS, BACKLOG §19.23). What has no Windows counterpart is nearly everything around the engine: the HTTP front (proxygen/folly), `ling-admin` and its 17,000 lines of Python node, server, Night Shift and audit code (`wc -l` on `dreamference/{node,vllm_server,night_shift,audit}`), systemd user units and lingering, bubblewrap and the AppArmor profile, Avahi, Docker and the Docker-network rule the gate enforces, PSI and earlyoom. The five gaps that decide the plan are in §10; the three measurements for the first day with hardware are in §9.

## 3. The memory partition, and what it means for a 57 GB engine

NVIDIA's Windows on Arm Porting Guide (*Unified Memory Architecture*, *Usage with CUDA APIs*, both dated 2026-09-10) is the one primary source, and it is specific:

- Physical memory is three regions: a **dedicated carveout** ("reported by Windows as dedicated GPU memory"), **shared system memory** (CPU and GPU), and **CPU-only** memory the GPU cannot allocate from. "The nominal shared system memory size is the post-carveout capacity minus 16 GB. That value is clamped to a minimum of 50% and a maximum of 80% of the post-carveout capacity."
- **`cudaMalloc`/`cudaMallocAsync`/`cuMemCreate` allocations "first land in the dedicated memory segment"**, where the driver applies "internal alignment, page-size, and mapping optimizations"; "when the dedicated memory segment is exhausted, new allocations spill to the shared segment", which is "backed by smaller pages … so access can be slower". **"Allocation placement is non-configurable."**
- `cudaMallocHost` lands in the shared segment and "is not L2-cacheable on the iGPU"; `VirtualAlloc2` + `cudaHostRegister` (2 MB-aligned) gives L2-cacheable coherent memory. The guide's recommendation: "keep intermediate buffers and model weights GPU-exclusive", coherent allocations only for "input and output buffers for AI inference".
- **Avoid `cudaMallocManaged`**: "technically supported" but on "a compatibility path that can lead to performance degradation". (The GB10 showed the same: managed memory streams at 161 GB/s against 258 for `cudaMalloc`, engine micro §2.)
- Reporting: `cudaMemGetInfo` reports dedicated **plus** shared; NVML (`nvidia-smi`) reports the carveout only; DXGI `QueryVideoMemoryInfo` folds both into the local segment, and the adapter descriptor's `DedicatedVideoMemory`/`SharedSystemMemory` give the two sizes.
- Budgeting: "Windows limits the GPU budget based on the total available system memory … Allocating the full GPU budget can leave too little host memory and can make the system unresponsive." Instead of polling, register `cudaDeviceRegisterAsyncNotification` for `cudaAsyncNotificationTypeOverBudget`: **trim callbacks** that fire on "a relevant budget change in either the dedicated or the shared memory segment", with "no single fixed threshold".

The rule checked against the one real reading. Microsoft's Task Manager screenshot of a Surface Laptop Ultra (StorageReview): **74.9 GB dedicated, 35.5 GB shared, 110 GB GPU total, 51.5 GB system memory**. With 128 GB installed, 74.9 + 51.5 = 126.4 GB is the usable total (1.6 GB reserved); post-carveout 51.5 GB; minus 16 GB = **35.5 GB**, inside the 50–80% clamp (25.8–41.2). The rule reproduces the screenshot exactly, so on that unit: GPU budget 110 GB, CPU-only 16 GB, and the rest of the CPU's memory is whatever of the 35.5 GB shared segment the GPU leaves alone. **Who sets the 74.9 GB carveout** (firmware, the OEM, or Windows' unified-memory setting) is still undocumented in anything read, as the Windows spec §1.2 already said; the Windows spec's own table assumed carveouts of 0–96 GB, and this reading says a real unit ships near 75.

What follows for the engine (estimates, from INTEGRATION §12's budget):

| | Linux node (GB10) | Windows node (that Surface) |
|---|---|---|
| Engine budget | ~57 GB: weights and drafter ~19, embedding and vision ~3.5, sessions 30, prefix store 2, scratch 2 (INTEGRATION §12) | the same 57 GB **fits inside the 74.9 GB dedicated segment**, so weights, KV and state never spill to the smaller-page shared segment; a unit with a smaller carveout would spill, which is measurement 1 (§9) |

## 4. Power, clocks and decode speed at 45–80 W (estimates from measured anchors)

Anchors, all measured on the GB10 by the engine project: a pure two-stream decode draws **44–45 W** at 2,405–2,476 MHz with no throttle reason for ten minutes (micro §4; the report calls it "a third of the 140 W budget"); replays with 25K-token prompts peak at **82 W** and 79 °C (M0); a single-stream speculative step is **~101 ms** today (BACKLOG §19.19, measured 2026-10-14: 102.0 ms at one stream), of which the 17.6 GB weight pass at the measured 257–262 GB/s is 67–68 ms and the rest, ~34 ms, is attention, DeltaNet, drafter, sampling and gaps that scale with SM clock, not with the bus (RESEARCH §16.9; micro §2: 8 SMs saturate the bus, so the stream itself does not care about clocks).

Two levers, separated:

1. **Bus.** 300.8 GB/s is 10% more than the GB10's 273. At the GB10's 94–95% efficiency, 285 GB/s, the weight pass is **~62 ms** instead of 67–68: a step of ~96 ms and about 5% more decode, *if* LPDDR5X at 9,400 MT/s holds that rate under the laptop's power cap. Unknown: whether DRAM power is inside the 45–80 W figure, and whether the memory controller is clocked down with the SoC on battery.
2. **Clock.** A 45–80 W budget covers CPU and GPU together; the GB10's decode alone sits at 44–45 W of GPU power. At the 80 W end of the range a laptop plausibly decodes **at or slightly above** GB10 speed (both levers positive). At the 45 W end the GPU runs at the GB10's decode draw with nothing left for the CPU, so the SoC clamps: if the SM clock falls to 70%, the ~34 ms grows to ~49 ms and the step is ~111 ms (−9%); at 50%, ~68 ms and ~130 ms (−22%). **Range: −22% to +5% single-stream decode against today's GB10 node**, every number an estimate until measurement 2.
3. **Prefill is the loser.** It is compute-bound, peaked at 82 W on the GB10, and will be clamped on every laptop setting: expect **0.55–1.0×** the engine's 2,100–2,600 tokens/s (README) depending on the power mode, i.e. the first answer of a new session and every long tool output cost more on a laptop than on a Spark. Microsoft's 923 tokens/s at 64K on a 137B MoE is consistent with a clamped prefill, not comparable in model.
4. **Battery.** 92 Wh (ServeTheHome) at 60 W system draw is about 1.5 hours of continuous decode; a node that serves overnight is a node on mains. Estimate.
5. **The Dev Box** at 100 W chassis against NVIDIA's 140 W desktop rating (StorageReview) is the closer stand-in for the GB10; whether its sustained power is 100 or 140 is a question for Microsoft, as StorageReview says.

The GB10 measurement shows no thermal headroom problem at decode; the laptop question is the *power* cap, and Windows' power modes (Best power efficiency / Balanced / Best performance, plus battery) are the knob the node must set and check, which `host check` today has no notion of.

## 7. Containment on Windows after 2026-10-07: MXC is GA

Microsoft Execution Containers became generally available on Windows 11 on 2026-10-07 (Windows Developer Blog; Windows Experience Blog). What it is: a JSON policy (files read and written, inbound and outbound network, "including whether the workload can connect to services through the host's loopback interface", desktop access) mapped onto a backend: a **process container** (AppContainer on Windows, Seatbelt on macOS, Bubblewrap on Linux), a **session container** (a separate Windows account and session), **WSLc** and a **MicroVM**; Enforcement, Learning and Permissive modes; an open-source SDK. Codex is on the list of agents that already support it; NVIDIA has integrated OpenShell into it. GitHub Copilot uses "the BaseContainer tier of the ProcessContainer backend" (Microsoft/GitHub post).

The Windows spec §7.4 refuses Codex's `mxc` sandbox level at `/airgapped on`, quoting MXC's pre-GA repository that no profile "should be treated as security boundaries currently". That quote is a month old and the product has shipped since. **Two items to re-evaluate, not decide here:** whether Codex 0.158's `mxc` level enforces the network policy in the kernel (if it does, it is a second enforced path for `on`, and a lighter one than two local accounts); and whether an MXC process container is the right shape for a node's **jobs** (a policy per job: the job directory writable, the home unreadable, no network). Unverified: GPU access from inside an AppContainer, and whether the policy's loopback rule can admit the model port alone.

## 8. A staged plan

**Stage 0, before a unit arrives (decidable now):**

1. **The toolchain question without a GPU.** Install the CUDA 13.4 Windows Arm64 toolkit on a `windows-11-arm` CI runner and compile `src/core/*.cu` with `-gencode arch=compute_121a,code=sm_121a` under MSVC. Either ptxas accepts the block-scaled MMAs or the engine has no Windows build at all; nothing else in this note matters until this is known. Same job: `safetensors.cpp` behind a `CreateFileMapping` branch, PCRE2 and ICU from vcpkg, `-fsanitize` under `if(UNIX)`.
2. **The HTTP front.** Decide whether `ling-serve`'s proxygen front is replaced for every platform or only on Windows. The clean cut is a small server over `ling_api` (which was built to be HTTP-free), or the engine as a child of a Rust front in the launcher that already speaks Codex's Responses API (`ling-rs`). Research item: try folly/proxygen's getdeps on Windows Arm64 once in CI and record the result, so the decision is informed.
3. **Python or Rust for the node half.** The Windows spec decided no Python on a Windows client. A node is different: the Python surface it needs (`node_serve.py`, `node_job.py`, `node_pairing.py`, the server lifecycle, the watchdog) is ~4,200 lines; `vllm_server_manager.py` and `hardware/model_downloader.py` import torch and tensorizer (`grep`, 2026-10-14), so a Windows node's Python would be trimmed of the tensorizer path, and CPython has Windows Arm64 installers (tier 3, Windows spec §16.1). Lay out both: a Python-on-Arm64 node with a trimmed dependency set, or the node half ported into the launcher (`ling node serve`, `ling serve`, `ling night run`). This is the decision that sizes the whole project.
4. **The service layout.** A design note for state under `%ProgramData%\Mightling` (weights, node id, advert state, jobs), services for the engine, the advert and the watchdog, their account, and the ACLs that let the sandbox accounts and the user read what they must.
5. **The MXC re-evaluation** of §7, from Codex's source at the pinned tag.
6. **Order the hardware** (the owner's decision of 2026-10-14: a Surface Laptop Ultra, 128 GB, 20-core, 2 TB; this supersedes the ASUS ProArt P16 of the Windows spec §21, question 4). The Dev Box in November is the closer stand-in for a mains-powered node.

**Stage 1, the first day with the unit:** the three measurements of §9, plus: compute capability and driver as the device reports them; `cudaMemGetInfo`, NVML and the DXGI descriptor side by side; the Windows client install (`install.ps1`), `ling node use` against a GB10 node, and the ETW audit, which were never run on a real Windows PC either.

**Stage 2:** the engine built natively, loaded, and put through its exactness gates (`--spec-check`, `--prefix-check`, the seeded replay against the GB10's outputs: the same bytes in, the same tokens out), then decode and prefill against the GB10 in each power mode and on battery. Gate for going on: single-stream decode within the −22% to +5% range of §4 with exact output; a clamp worse than that is a product decision about the laptop, not an engine defect.

**Stage 3:** the node services and the forced command, in the language of Stage 0.3; `node add` from a GB10 to the laptop and back; a lane for Night Shift; the Windows node's own audit run.

**Stage 4:** jobs and their containment (Job Object plus sandbox accounts, or MXC), and the freeze test of the Windows spec §9.4 under the engine's real budget.

## 9. The first three measurements

1. **Bandwidth by segment.** `bench/membw/membw.cu` built for Windows, unchanged in what it does: a read stream over 8 GiB from (a) a `cudaMalloc` buffer in the dedicated segment, (b) a `cudaMalloc` buffer forced into the shared segment by first filling the dedicated one, (c) `cudaMallocHost`, (d) `VirtualAlloc2` + `cudaHostRegister`; and the SM-count curve (micro §2 found 8 SMs saturate the GB10's bus). Expected: (a) near 285 GB/s; (b) lower by the smaller pages; (c) lower still. Then the DXGI descriptor and `QueryVideoMemoryInfo` while a 57 GB `cudaMalloc` set is resident, to see that it sits in the dedicated segment. This measurement decides whether the engine's budget needs a carveout floor and what `host check` must read.
2. **Sustained decode and prefill power.** micro §4's protocol: ten minutes of two-stream decode on the engine (or on `llama-server` before the engine builds) while `nvidia-smi --query-gpu` samples clocks, power, temperature and throttle reasons once a second, in each of Windows' power modes, on mains and on battery; then the same with 25K-token prompts. This gives the real number for §4's range and the first reading of the 45–80 W clamp.
3. **The partition and the trim.** Allocate in 1 GB steps past the dedicated segment and then past the GPU budget, recording where allocations spill (bandwidth of the newest buffer), when `cudaAsyncNotificationTypeOverBudget` fires and what the driver does to a process that ignores it; then the Windows spec §9.4 freeze test: a second process eating host memory in 1 GB steps until the watchdog trips, with input latency measured. This is the measurement the host-safety layer is rebuilt on.

## 10. The five gaps that decide the plan, and the risks

Gaps, largest first:

1. **The engine's platform layer**: proxygen/folly for `ling-serve`'s HTTP front (unverified on Windows Arm64, likely not worth porting), `mmap` in `safetensors.cpp`, pkg-config, MSVC as nvcc's host; and above all **whether the Windows Arm64 toolchain compiles `sm_121a` block-scaled kernels for N1X**, which nothing read confirms.
2. **The node half has no Windows implementation and no decided language**: `serve-job` (the forced command), the server lifecycle, the watchdog, Night Shift's runner, jobs; ~4,200 lines of Python in a product that decided no Python on Windows.
3. **A node runs with nobody logged in**: services, a service account, state under `%ProgramData%`, ACLs for the sandbox accounts, the OpenSSH Server's `administrators_authorized_keys` rule, Modern Standby and lid-close policy. None of this has a counterpart in the client spec.
4. **Containment of jobs and `/airgapped on` after MXC's GA**: Job Objects cap only committed CPU memory; "no GPU" and "no network" for a job need the sandbox accounts' WFP block or an MXC process container; the Windows spec's refusal of `mxc` rests on a pre-GA quote.
5. **The gate and lanes**: the model gate's SWE-bench rule has no Docker network to refer to; the gate becomes a loopback proxy or firewall policy, and a Windows node is a lane only.

Risks:

- **CUDA on Windows on Arm is three months old** (developer preview driver 2026-07-16, toolkit 2026-09-09 per the Windows spec §1.1; the device driver floor 616.41 from the 13.4.2 notes). The driver, not the engine, is the likeliest source of a wrong result or a slow path, and the exactness gates are the way to see it.
- **The carveout is set by someone other than Mightling.** A unit with a small carveout spills the weights into the shared segment; the engine cannot choose placement (porting guide). Mitigation: measure, and refuse to serve below a floor the way `check_host_safety()` refuses an unsafe host.
- **Power.** At 45 W the decode estimate is −22%; prefill worse. A laptop node on battery is a slower node, and a sleeping laptop is no node. The product has to say so.
- **No bwrap.** Every containment story on Windows is accounts, ACLs, WFP, Job Objects or MXC; none gives the single `--unshare-net` line Linux does, and the Linux jobs' "home hidden" is an ACL exercise.
- **Unsigned binaries on a consumer laptop**: Smart App Control blocks them (Windows spec §16.3), and Defender may submit `ling-serve.exe` to Microsoft; a node install that ships 20 GB of weights beside an unsigned engine is the case for signing before a node is offered.
- **Upstream churn** in Codex's Windows sandbox and in MXC (Windows spec §20.5).

## 11. What this means for the roadmap

Nothing here precedes the engine's own order (the moonshot's P1, M4's stage 5, cuBLAS removal, BACKLOG §19.23): a Windows node is a port of a finished engine, and §19.23 and the HTTP-front decision make that port smaller. The one thing worth doing before the laptop arrives is Stage 0.1, the compile-only toolchain check, because its answer is binary and everything else waits on it. The Windows *client* spec's phases 3–4 (bring-your-own server, then W1) remain the fastest way to a laptop that serves its own model; this note's node is the step after that, and it is a product decision whether a 45–80 W laptop should be a node at all or only a client that serves itself.
