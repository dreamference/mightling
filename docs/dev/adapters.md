# LoRA adapters

Developer notes for `ling-admin adapter` and serving adapters on the default model. Spec: `specs/DREAMFERENCE_MIGHTLING_ADAPTERS.md`; the probe that decided what is served: `docs/dev/lora-serving-probe-2026-10-19.md` on branch `research/lora-serving-probe`.

## Installing (`dreamference/hardware/adapter_*.py`)

- `AdapterManifest` parses `manifest.json` strictly: unknown schema or key, a missing key, a file that is not safetensors or JSON, a path leaving the folder, a digest that is not sha256, all refused.
- `AdapterSignature` checks the SSHSIG signature with `ssh-keygen -Y verify` under the namespace `mightling-adapter`, against `RELEASE_KEYS` (the lines of `ling-rs/release-signing.pub`; a test keeps them equal). A `mightling-release` signature never passes as an adapter's.
- `AdapterVerifier` is the one check `install`, `verify`, a receiving node and `server start` share: the catalogue's pin of the manifest, the manifest, the signature (waived only for an adapter installed with `--third-party`), every file's sha256, the configuration and the tensors against the recipe's `lora` key (attention and GDN modules only, rank ceiling), and the base. The base is asked of the server (`/v1/models`); with none answering, the configured model stands in.
- `AdapterBaseDigest` takes the digest of §5.2 without reading the weights: a weight file in the hub cache links to a blob named by its sha256, so the link target is its hash; only the small files are hashed. Cached by (repo, revision) in `~/.cache/dreamference/adapters/base-digests.json`.
- `AdapterInstaller.install` fetches `manifest.json` and its signature alone first, checks them and the base, and only then fetches the files the manifest lists (`allow_patterns`). Files live in the hub cache as a snapshot at the pinned commit; `installed.json` (`AdapterStore`, 0600) records the snapshot relative to the hub, so the engine's container finds it under its own mount.
- `ADAPTER_CATALOG` (`adapter_catalog.py`) is empty until the first adapter meets the publishing bar; the organisation's slug `dreamference` is assumed (spec §17, question 9).

## Signing (`.github/workflows/adapter-sign.yml`, `scripts/adapters/sign_manifest.py`)

Manifests are signed in CI, never by hand (spec §5.1). The input is a manifest committed to this repository at `adapters/<name>/<version>/manifest.json`, the folders naming the manifest's own `name` and `version`, with `source.json` beside it: `{"repo": "dreamference/mightling-<name>", "commit": "<40 hex>"}`, the adapter's Hugging Face repository and the commit its weights were uploaded at (the manifest has no field for either, and its parser refuses unknown keys). A push of one to `main` runs the job in the `release` environment:

- `check`: `AdapterManifest.parse`; every listed file's sha256 against the repository's metadata at that commit (LFS files by their recorded sha256, the few small files downloaded, checked against their git blob id and hashed); `base` and `drafter_base` against the registry's pins (the matrix entry's `revision`, its `speculative_config` drafter); and each digest against `AdapterBaseDigest.compute` over a snapshot staged from the base repository's metadata (weights as links named by their LFS sha256, as in the hub cache), so publishing and installing take the digest with the same code.
- `sign`: checks again, writes `manifest.json.sig` with `ssh-keygen -Y sign -n mightling-adapter` (the key a 0600 file for that step only), and verifies it with `AdapterSignature` against `ling-rs/release-signing.pub`; a key that is not a release key stops the job. The pair is attested (build provenance).
- `publish`: checks and verifies again, uploads both files as one commit whose parent is exactly the checked commit (`HF_ADAPTER_TOKEN`), and writes the catalogue entry; `catalog` adds it to `ADAPTER_CATALOG` and the job opens the pull request.

Any failure stops before anything is signed or uploaded. `publish --dry-run --key <file>` checks and signs with a key of your own and never uploads; `tests/test_adapter_signing.py` runs it with session keys and the hub mocked. The repository must allow GitHub Actions to create pull requests (Settings, Actions, General).

## Paired nodes

`node sync-model` follows a successful model copy with `NodeAdapterSync.send`: one `adapter-receive <name> <repo> <commit> <size>` per installed adapter that Dreamference signed for that model, a tar of its cache folder over the same forced command. The receiving node unpacks into a staging folder, checks the blobs and the adapter itself (its own key list), and only then merges and records it. A third-party adapter is never sent.

## Output

New modules outside `dreamference/cli/` may not `print` (the quality ratchet's T201): the installer raises `ValueError` with the reason and returns entries, `AdapterCommand` (`dreamference/cli/adapter_command.py`) prints, and the receiving side of a sync writes its JSON line and refusals to the SSH session's own streams.

## Serving (`dreamference/vllm_server/adapter_serving.py`, `model_gate_adapters.py`, `sglang_runtime_patcher.py`)

- **Flags only when an adapter is installed.** `build_launch_command` asks `AdapterServing.launch_adapters` for the installed adapters of the model being launched that pass `AdapterInstaller.verify` (memoized per file stamp). None: the server's arguments are byte for byte what they were, so a node without adapters has nothing to recompile and the drift check nothing to report. Some: the recipe's `lora` key (`QWEN38_LORA_RECIPE`, on the default entry only, never on Minima, whose every layer is NVFP4) becomes `--enable-lora --max-lora-rank 16 --max-loras-per-batch 4 --max-loaded-loras 8 --lora-strict-loading --lora-paths <name>=<snapshot>… --api-key <key>`, as the probe's launch 4 ran it. There is no `--lora-target-modules`: on v0.5.21 its choices do not list the GDN modules, so the pool's module set comes from the adapters given at start, and an adapter installed later with other modules needs a restart (as does the first install: `install` says so).
- **Only behind the gate**, and only without a caller's own `--api-key`: the gate is the loader and holds the engine's key. A start whose gate fails serves the base alone.
- **The engine's key** (`engine.key`, 0600 in the gate's folder, made once so the launch line is stable) is `--api-key`, not `--admin-api-key`: with an admin key alone SGLang leaves `/load_lora_adapter_from_tensors` (which has no auth level) open, while `--api-key` keys every endpoint but `/health*` and `/metrics`. The gate replaces whatever `Authorization` a client sent with the key on every request it forwards; `ling-admin`'s own probes go through the gate.
- **The runtime patch.** `/v1/responses` on v0.5.21 builds its `GenerateReqInput` without the adapter (the probe). The recipe carries the fix as anchor substitutions of `serving_responses.py` with the image and the sha256 of the image's own copy; `SGLangRuntimePatcher` copies the file out of the image (`docker create`, `docker cp`, `docker rm`), checks the pins, applies each anchor exactly once, writes `~/.cache/dreamference/sglang-patches/<file>-<pin>-<digest>` and the launch mounts it read-only over the original. The same file carries the recipe's own patch, mounted on every launch (the phase-gated history merge, [models-and-engines.md](models-and-engines.md)): with adapters the launch mounts one file with both patches (`SGLangRuntimePatcher.for_launch`), without them the recipe's alone. A file that is not the pinned one, or an anchor that no longer matches, means the start serves no adapters, never a wrong file (for the recipe's own patch it stops the start).
- **The gate's list.** `server start` (`AdapterServing.prepare`) writes `adapters.json` beside the gate's run record: the served base's id, `max_loaded`, and per adapter its container path, file hashes and display fields. The gate reads it on every request; `adapter remove` takes the adapter off it (`withdraw`), so its next request is a 404. While the list exists the gate's container also mounts the hub cache read-only, to hash an adapter's files before it loads it.
- **The gate's rules** (`model_gate_adapters.py`, copied beside the service into its container; standard library only): load and unload endpoints are 403 on the public port whatever the state; a generation request's body (`/v1/responses`, `/v1/chat/completions`, `/v1/completions`, at most 64 MiB) is read whole only while the list exists; `lora_path` or a `:` suffix from a client is 400; `<base>+<name>` not in the list is 404 `adapter_not_installed` (another base: `adapter_base_mismatch`); a listed one is loaded on first use (one load under concurrent requests, its files hashed first, the least recently used unloaded past `max_loaded`), the body is re-serialized with `<base>:<name>`, and the answer is streamed back with `"<base>:<name>"` swapped for `"<base>+<name>"`, the same length, across read boundaries. `/v1/models` is answered by the gate: the engine's base entry, the engine's own adapter entries (bare names, with a `parent`) dropped, and one entry per listed adapter in the shape of the spec's §10.1.
- **Host safety.** The GPU pool is inside `--mem-fraction-static` (it displaces KV cache: about 0.17 GiB per slot at rank 16 on these layers, measured); the loaded adapters are host memory, so the container's cap grows by `max_loaded_loras` times the largest adapter.

## Adapters need SGLang while ling-serve cannot serve them

ling-serve, the default engine since 1.8.0, has no adapter code until 1.8.1. When the engine a `server start` resolves is ling and an adapter is installed for the model (`AdapterServing.launch_adapters`), `_engine_for_adapters` in the CLI controller starts SGLang instead and prints one line saying so; `--engine ling` with an adapter installed exits 2 rather than start without it. `ling-admin adapter install` warns when the configured or default engine is ling. Since the 1.8.0 switch this is the path every adapter user takes without a flag. Remove it when ling-engine serves adapters (1.8.1).
