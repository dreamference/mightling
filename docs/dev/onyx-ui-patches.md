# Patching Onyx's web UI

Developer notes behind the web-chat line in `AGENTS.md`. Spec: `specs/DREAMFERENCE_ONYX.md`. Deployment and `configure()` are in [onyx.md](onyx.md).

There are four kinds of patch, each in its own module under `chat/`: fonts *substitute* rules Onyx ships, overrides *append* rules it does not have, labels *rewrite* strings in the compiled JavaScript, and scripts *add behaviour*. All of them are applied by `ling-admin chat configure`.

## Fonts: swapped at the `@font-face`, not at the `font-family`

`chat/onyx_ui_fonts.py` makes Onyx look like Telegram by replacing the three faces it ships (Hanken Grotesk for the interface, KH Teka for a few headings, DM Mono for code) with Roboto and Roboto Mono. Onyx names its UI face in around forty CSS declarations, most through the `--font-hanken-grotesk` variable `next/font` writes onto `<html>`; rewriting the four `@font-face` blocks instead leaves every declaration alone and only changes which file the name resolves to, so **the served CSS still says `Hanken Grotesk` everywhere and renders Roboto**.

Roboto is fetched once from google/fonts, converted from variable TTF to WOFF2 with fontTools on the host, cached in `~/.cache/dreamference/fonts`, and served by Onyx itself from `/app/public/fonts`: no font CDN at page load.

One non-obvious step: Next.js builds its static routes from `public/` **at boot**, so a face copied into a running container is on disk with no URL until the server restarts; `install()` restarts it, but only when it actually copied something. The stylesheets need no restart, being read per request.

## CSS: Dreamference's own rules are appended, not substituted

`chat/onyx_ui_overrides.py`. Twenty-nine named rules, each a `Final[str]` constant concatenated into `UI_OVERRIDES`, covering the Telegram-style look (white sidebar, white canvas, Tiffany-tinted message bubble with a shadow, black message text, Tiffany selected row and unread badge) and the chrome that is switched off (agents and projects sections, the search palette's projects group, the Add Model button, the model chip, the sidebar mark, the Share button, the version footer, the Help & FAQ link, and the Chats and Memory cards in Chat Preferences). Most of the work is in *how each is anchored*, and the recurring lessons are worth more than the list:

- **Specificity against Onyx's own rules.** Onyx styles a sidebar row as `.interactive[data-interactive-variant=…][data-interactive-state=selected]` (a class and two attributes) and its hover rule adds `:hover:not([data-disabled])`. An override must mirror that shape exactly and win on source order; the first attempt dropped the leading class, lost the tie, and left the row grey.
- **Redefine the token, don't repaint the element.** Message text is black because `--text-04`/`--text-05` are redefined on the message containers, not because anything sets `color`: `.text-text-04{color:var(--text-04)}` still wins as the rule and simply resolves to our value. The same trick beats an *inline* style: the unread badge's colour is inline and unbeatable without `!important`, but its value is `var(--action-link-05)`, so redefining that token in the sidebar's scope recolours it with an ordinary rule. **Where the inline value is a literal there is no such escape**: Onyx sizes the avatar initials with an inline `font-size`, and shrinking them to one letter (`font-size:0` plus `::first-letter` restoring the size) needs the file's only `!important`.
- **Anchor to what a build cannot renumber**: `data-testid`, `data-*` state attributes, `aria-label`, Onyx's hand-written BEM classes (`opal-…`), and, for the two logo SVGs, which have neither, the `viewBox`, the same 64×64 grid `ONYX_LOGO_PATHS` keys its path substitutions to, so the two break together rather than one silently missing. Never Tailwind utilities, which are a fresh permutation each build.
- **`:has()` for sections with no handle at all.** The agents section is `:has(>[data-testid="AppSidebar/more-agents"])`; the search palette is a flat list where headings are siblings of entries, so its Projects heading is `*:has(+[data-command-item="new-project"])`: "whatever sits directly above New Project". The sidebar's projects section has no handle even by that route and is identified as the one `flex flex-col` section that is *not* the agents one, which is the weakest grip in the file and marked as such.
- **One thing CSS could not do, and the file says so.** Moving the model chip onto the composer's toolbar row was attempted three ways: absolute against an inherited containing block, absolute against a named one, and kept in flow with `order` and a negative margin. Each was right on the chat page and wrong on the new-chat page, because the chip is not a descendant of the composer box and the two are not even siblings there. The chip is now simply hidden, and the three failure modes are recorded in `onyx_ui_overrides.py` so a future attempt starts from the JSX, which is where it has to happen.
- **Scope a rule to the half of the UI it means.** `SIDEBAR_TEXT_CSS` blackens chat titles but is confined to `.opal-sidebar-body__content`, because the same selector unscoped also hit New and Search in the header and made navigation as loud as content; those take `--text-02`, the token the "Recents" section title uses. And `AGENT_AVATAR_CSS` is deliberately *not* scoped to `[data-testid="onyx-ai-message"]`: Onyx sets that test id only once a message completes, so scoping there left the avatar on screen for exactly as long as an answer was streaming.
- **Auto-hiding the sidebar means taking it out of flow.** `SIDEBAR_HOVER_CSS` uses `position:fixed` plus a transform rather than a width transition, because a width change still reserves the space and Onyx's own folded state is a `data-folded` attribute only JavaScript sets. A 10px sliver is left on screen deliberately: with `translateX(-100%)` there is nothing to hover and no way back to the chat list without a keyboard.
- **Hidden, not removed.** Nothing leaves Onyx's bundle; dropping a constant from `UI_OVERRIDES` restores the feature on the next `ling-admin chat configure`.
- **Two scoping rules that are load-bearing.** Every white surface and every black text rule is scoped `html:not(.dark)`, because those tokens are *white at partial alpha* in dark mode and forcing them black would erase the UI. And `display` versus `visibility` matters where layout is a grid: the per-message avatar is hidden with `visibility` because the timeline rail is what the header row and the indented body are aligned against.

The block is appended to *every* stylesheet under `.next`, because Next.js splits CSS per route and no single sheet is loaded by every page. `OVERRIDE_MARKER` opens it and everything after is Dreamference's, so a re-run cuts at the marker and rewrites: appending only when the marker is absent would make later edits to the CSS unappliable.

## Labels: the third kind of patch

`chat/onyx_ui_labels.py` rewrites strings in the compiled JavaScript, because a label is text in a JSX call and no stylesheet can reach it. (`content` on a pseudo-element covers text up, but the original stays in the accessibility tree and in find-in-page, which is worse than not doing it.) Each rewrite matches a *quoted* string literal, and where the wording is common it also carries the React prop it is passed as, never the bare word: `New Session` and `Search Chats` also occur in analytics event names and aria labels, and replacing them there renames things that are not this sidebar.

## Scripts: the fourth kind of patch

`chat/onyx_ui_scripts.py`. Stylesheets are appended, strings are rewritten, and this adds *behaviour*: an element that is not in Onyx's markup at all and cannot be conjured by either of the others. There is no sanctioned injection point in this edition: `custom_analytics_script` is in the route table but is an Enterprise feature and answers 404, so the script goes into the bundle the way the stylesheets go into the CSS. It is appended **only to the chunks that already mention `opal-sidebar-footer`** (the chunk that renders the element being attached to), so it arrives when its anchor exists and a page without a sidebar never runs it. The whole block is wrapped in a guard and a `try`: a throwing top-level statement in a bundle chunk takes the application down with it.

**Two traps, both of which made an injected script silently do nothing.** Turbopack ends each chunk with a `//# debugId=…` line comment and *no trailing newline*, so a block appended directly onto the end sits inside that comment and never runs: no error, nothing in the console, the page simply behaves as though the patch were absent. `append_scripts` trims trailing newlines from what it keeps and writes exactly one. And the webview caches chunks like any other immutable asset, so a fixed script can still look broken; verify with a fresh cache.

### WebKitGTK paints its scrollbar as engine chrome that CSS colours cannot reach

Written when the desktop app was the Tauri shell on WebKitGTK (until 2026-10-07; the Electron app renders with Blink, see [desktop.md](desktop.md)). A `get_snapshot` of the rendered page shows *no* non-white pixel anywhere near the sidebar's edge, yet the line is on screen: the trough is drawn outside the page. Track colour, `border:0` and `box-shadow:none` all leave it. The only property the engine honours there is `scrollbar-width:none`, so in a WebKitGTK view the native bar is suppressed entirely and **`onyx_ui_scripts.py` draws the scrollbar instead**: one fixed-position thumb, geometry derived from the scroll container per update, styling in `CUSTOM_SCROLLBAR_CSS`.

Three of its choices are load-bearing: the container is re-queried on every update because React recreates the chat list wholesale; `scroll` is listened for in the *capture* phase because scroll events do not bubble; and a 1s interval catches what no event announces, content changing the scrollable height. Blink keeps its native hover-revealed scrollbar and the script refuses to run there. Verified in an offscreen WebKitGTK view: thumb at the sidebar edge, tracks `scrollTop`, hides when the list fits.

## Verifying a UI patch

**Tests run the script.** Injected JavaScript is tested by *running* it: `tests/test_onyx_ui_scripts.py` executes the real script under node against a stub DOM in all three states, rather than asserting on the source text.

**In WebKitGTK.** Load the page in an offscreen WebKitGTK view: `sudo apt install python3-gi` (the `gir1.2-webkit2-4.1` typelib is already present), then `WebKit2.WebsiteDataManager.new_ephemeral()` → `WebContext` → `WebView` inside a `Gtk.OffscreenWindow`, log in with a `fetch` from the page's own origin, and `evaluate_javascript` for computed styles or `elementFromPoint` probes. It needs the system Python, not `.venv`. This is how the comment trap was found and how `scrollbar-color` support was confirmed rather than guessed, and it captures nothing from the user's screen, unlike a screenshot.

**In Chromium: logging in means a same-origin page.** The Onyx chat view is client-rendered and behind auth, so `curl` shows an empty shell and a headless screenshot shows the login form. The way through: `docker cp` a scratch HTML file into `/app/public`, restart (Next.js builds its static routes at boot), then point headless Chromium at it. The page can `fetch('/api/auth/login')` and iframe `/app?chatId=…` because it is same-origin, and `frame-ancestors 'self'` permits the frame. From there `getComputedStyle` answers what actually applied. Two traps: overwriting that file needs no restart (only *new* routes do), and **the Chromium profile caches the CSS chunks**: reuse `--user-data-dir` across runs and you will verify against the stylesheet from before your change.

Tests never apply these patches to a running container: conftest stubs the UI-patcher methods ([testing.md](testing.md)).
