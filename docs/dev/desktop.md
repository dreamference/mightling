# The desktop app

Developer notes behind the desktop line in `AGENTS.md`. Spec: `specs/DREAMFERENCE_MIGHTLING_DESKTOP_ELECTRON.md`, whose §9 records what was built and measured.

The desktop app is Electron, built the way the Codex desktop app is built, with `ling` inside (`chat/desktop_runner.py`, project in `desktop/electron/`, Work's UI in `desktop/ui/`).

## Why Electron

Until 2026-10-07 it was a Tauri shell on the system's WebKitGTK, and typing into it on this GB10 trailed the keys: WebKitGTK's one GPU path asks the DRM device for a dumb buffer, which the proprietary NVIDIA driver refuses, so the app drew on the CPU at 40–50 ms per keystroke frame in a near-full-screen window (measured in an offscreen view, ELECTRON §1). Chromium renders through ANGLE on NVIDIA's own GL and never asks.

## Shape

- Electron is **stock 42.x, pinned to a patch release** (the Codex app runs the upstream vendor's own build of the same major). Forge 8 packages it (`maker-deb`; Forge 7 until 2026-10-09, ELECTRON §12); Vite builds the main process (`src/early-bootstrap.ts` → `bootstrap.ts` → `main.ts`) to `.vite/build/early-bootstrap.cjs`, the preload to `preload.cjs` (Forge 8 emits both as `.cjs`) and the page's React UI.
- `app.json` holds the product name, identifier, scheme and the window's settings (under `work`, its old name), read by the app and by the Python side alike.
- **Several windows, one app-server** (DESKTOP_ELECTRON §13, the owner's decision of 2026-10-22; one window from 2026-10-09, ASK §18.6, until then). The `ling app-server` the app starts is its only one, whatever the number of windows: full windows (File › New Window, Ctrl/Cmd+Shift+N), a thread popped out, and the terminal or the diff detached into a window of its own. The menu's Ask and Work, the tray's, `ling app`, a link and a second instance bring the most recently focused full window forward on the view asked for (`showView` in `main.ts`), or open one when none is open; the single-instance lock stays, so no second app ever starts. Every window is made by `openWork` (`work.ts`) with the same preload, sandbox, CSP and navigation lock (`work.test.ts`). The full windows open at a quit (or the last one closed) reopen at the next start where they were (`windows.json`, `WindowSession` in `window-state.ts`; not in the audit's session); pop-outs and panes keep only their last bounds. Until 2026-10-09 the menu's Ask opened a separate window on `ling web` (`chat.ts`, `web.ts`, now removed), whose own app-server shared `~/.mightling` with the window's; the app no longer starts, signs in to or loads `ling web`, which is unchanged for browsers.
- **The app window** (the former Work window) loads `app://-/index.html` from the asar (`app-protocol.ts`: a privileged scheme serving the bundle with a strict CSP, cancelling requests from any other origin) and talks to the main process over **one IPC channel** behind `window.electronBridge.sendMessageFromView`, answered only for the app's own windows' `webContents` and routed per window (below). A refusal comes back as `{ __mightlingFailed: message }` and the preload throws it in the page (`failure` in `api.ts`): a throwing handler would reach the page too, but Electron logs each one as "Error occurred in handler". SIGTERM and SIGINT quit the app as the menu's Quit does, stopping the tasks and the agent's server first, and end it after five seconds if the quit has not finished (a Mac once kept its window after a SIGTERM). It shows **Ask and Work** one click apart, as `ling web` does (`#work` opens Work; no argument opens Ask; the menu's Work entry, `--work`, a folder, a thread or a `mightling://` link open it on Work, and a `view` message switches the window when it is already open; ASK §18).
- **One policy for both hosts** (ASK §2.3): `policy.ts` compiles in `ling-rs/web/policy.json`, the file `ling web` compiles in, and `policy.test.ts` runs every case of `ling-rs/web/vectors/outgoing.json` with the shared stubs. The allow-list (a Python test checks it against the committed protocol types), the dropped thread fields, the named prompts, answers only to pending server requests. For an Ask thread the main process does what `ling web` does (`ask.ts`, `server.ts`): composes the named prompt with `ling prompt show <name> --composed` in `$CODEX_HOME/ask` before vetting, creates `ask/q-<hex>` (0700), confines the thread to it, links `ask/<thread-id>` to it once the server answers, and writes attachments there (`ask/upload`, base64 over the same channel, `ling web`'s caps and file-name rules). `bridge.ts` keeps `classify`, the busy marker Night Shift reads (`server.ts` writes it) and finding `ling`.
- `server.ts` spawns `<resources>/ling -c features.code_mode_host=true app-server` with `LOG_FORMAT=json`, `RUST_LOG=warn` and the resources folder on PATH, as the Codex app spawns its agent. `ling` and `codex-code-mode-host` are copied from the installed build into `desktop/electron/resources/` by `desktop build` (the release workflow takes them from the `ling` job's artifact) and ride along as extra resources.
- On a client, Ask runs in the app window on the app's own app-server, against the node's model server, which the bundled `ling` finds; the TCP forwarder to the node's port 3000 and the app's own node discovery were removed with the Onyx window; see [node.md](node.md).

## Six things to keep

1. **No GPU switches, no `WEBKIT_*`, no `GTK_THEME`, no `--no-sandbox`**: Electron's defaults, as the Codex app runs. A test greps the sources for each.
2. **Chromium's sandbox needs a user namespace, and Ubuntu refuses one to programs without an AppArmor profile** (the same `kernel.apparmor_restrict_unprivileged_userns` rule as `bwrap`, see [host-safety.md](host-safety.md#bubblewrap-needs-an-apparmor-profile-and-this-machine-now-has-one)). The `.deb`'s `postinst` writes `/etc/apparmor.d/mightling` (`profile mightling "/usr/lib/mightling/Mightling" flags=(unconfined) { userns, }`, the Codex app's shape) and loads it; `prerm` removes it; **no `chrome-sandbox` SUID helper is shipped** (the packager's `afterCopy` deletes it). For a checkout, `desktop install` writes `mightling-desktop-dev` for npm's `electron` and the packaged binary, with sudo, announced first; the packaged path (`out/Mightling-linux-<arch>/Mightling`, `DesktopRunner.packaged_binary_path()`) is named before it exists, since `install` runs before the first `run` packages the app (until 2026-10-19 it was left out, and the binary the launcher entry starts died with "No usable sandbox!"). Whether a binary is covered is read from the profile files (`DesktopInstaller.covering_profile()`, any file in `/etc/apparmor.d` naming its quoted path with `userns,`), not from `userns_allowed()`, which stays false for unconfined programs however many profiles there are; `run` and `status` say when the binary they start has none. **An unpacked build** (the zip, or `out/Mightling-linux-<arch>/` copied to another machine; client testing 2026-10-19) has no installer of ours and, on a client, no `ling-admin` (clients are wheel-free): the `postPackage` hook copies `linux/install-sandbox-profile.sh` beside the binary, which writes `mightling-unpacked` for the folder it is in after printing its two sudo commands, and does nothing where a profile already names the binary (it also lands in the `.deb`, where the package's own profile does). The error cannot be caught in the app: Chromium's zygote host aborts before the main process's JavaScript runs. `ling app` (`ling-rs/src/app.rs`) writes the app's output to `$CODEX_HOME/log/ling-app.log` and watches the app for three seconds: an app that ends with a failure in that time is reported with the log's last lines and, for a sandbox failure, the commands that fix it; an exit 0 (a second instance handing off to the open window) is success. Until 1.7.1 the output went to null and the app failed silently from there. From a terminal under PyCharm's permissive profile the app starts without any of this, which is why the problem only shows from the launcher or a plain terminal: `DesktopInstaller.userns_allowed()` asks as an unconfined program would (`aa-exec -p unconfined`). **Without sudo** (2026-10-22, NO_SUDO §5.3): where no profile covers a binary the user owns, `ling app` starts it with `CHROME_DEVEL_SANDBOX` naming a root-owned setuid helper an installed Chromium browser ships (Google Chrome's `/opt/google/chrome/chrome-sandbox` first), and says so; measured, the zygote gets fresh PID and network namespaces and the renderers seccomp. With neither, it says before starting that the app will stop and what an administrator runs.
3. **Egress is closed in the main process and checked by `ling-admin audit egress --app`.** `egress.ts` always passes `disable-background-networking`, `disable-component-update` and `disable-features=AimEnabled,AutofillServerCommunication,NetworkTimeServiceQuerying,MediaRouter`; permission requests are denied except clipboard writes and the microphone, audio only, for the app's own page (`grantsRequest`; dictation, ASK §7: the recording goes to the main process as `voice/transcribe`, which posts it to the speech-to-text sidecar on `127.0.0.1:8100`); `app://-/images/<id>.jpg` serves the image search store read-only (`imageFile`, ASK §6); the spellchecker's dictionary download is pointed at `app://` (so it fails locally) and `window.open` goes to the system browser. Fuses: `RunAsNode`, `EnableNodeOptionsEnvironmentVariable`, `EnableNodeCliInspectArguments`, `GrantFileProtocolExtraPrivileges` off; `EnableCookieEncryption`, `EnableEmbeddedAsarIntegrityValidation`, `OnlyLoadAppFromAsar`, `WasmTrapHandlers` on; flipped by a `postPackage` hook with `@electron/fuses` 2, because Forge 7's own fuses plugin pinned the 1.x line, which has no `WasmTrapHandlers` (Forge 8's takes 2.x; the hook stays, since it also deletes `chrome-sandbox` and re-signs a Mac bundle). The audit's app mode starts the packaged (or installed) app as `ling app` does, with no argument and `MIGHTLING_APP_AUDIT=<seconds>` (the window hidden on Ask, its app-server started, quit by itself), in a scratch `HOME` and `CODEX_HOME`, with the `exec` session's allowlist: since the fold a connect to `ling web`'s 3100 is a finding, as one to Onyx's 3000 is; it needs a display (`DISPLAY` or `xvfb-run`), because Electron's `--ozone-platform=headless` SIGSEGVs on this machine.
4. **The data folder stays `~/.local/share/dev.dreamference.mightling`** (`app.setPath("userData", …)` after `app.setName`), so `ling app` keeps emptying the HTTP cache there (now Chromium's `Cache`, never its `Cookies`) and the rename migration's move still lands. The window's bounds are persisted beside it (`window-state.ts`, clamped to a display's work area).
5. **The app window is frameless with native controls** (`titleBarStyle: "hidden"`, a transparent `titleBarOverlay`, 36 px), so the page's own header bar is the title bar: `-webkit-app-region: drag` on `.bar`, `no-drag` on its controls, and 150 px of right padding under the overlay's buttons, all under `html[data-host="electron"]`, since `ling web` serves the same page to browsers and phones.
6. **The app signs in to nothing and handles no password.** Its app-server is its own child on stdio, so there is no session to hold. The Onyx password sign-in (`sign-in.ts`) went with the Onyx window and the `ling web` one-time link (`ling web open --print-url`, which `ling web` still offers) with the separate Ask window; `credentials.test.ts` checks that no bundle, the main process's included, carries a credential string or that link.

## Also

- **`ling airgapped --thread <id>`** is how Work learns a thread's air-gap level (`airgapped.ts` parses the first line): the launcher's own resolver, not a fourth copy of the crate.
- **Strict confinement is for `/airgapped on`; at `off` the app behaves like Codex's** (owner's decision, 2026-10-22). `policy.json`'s `airgappedRefusedRequests` lists the requests allowed only at `off` (the plugin installs, and `thread/shellCommand`, with its reason in `airgappedRefusalReasons`); `thread/shellCommand` is, the composer's `!` command (`parseShell` in `composer.ts`, `runShell` in `App.tsx`), which Codex runs in the user's own shell, unsandboxed, and which is user-initiated, never the agent's. It starts a turn, so it is one of `windows.ts`'s `COMPOSER_METHODS`: only the thread's composer window sends it. An install is judged by the configured level; the `!` command by the level of the thread it names (`airgapped_on(thread)` / `airgappedOn(thread)` on the policy's source, `airgapThread` in `policy.ts`): `ling web` calls `ling_airgapped::resolve`, Electron's main process runs `ling airgapped --thread <id>` before vetting (`airgappedOn` in `airgapped.ts`, which fails closed: no answer is `on`). Each resolves in its own folder and, when the server has named the thread's folder (`threadPlace`, from `thread/started` and the thread openers' answers), in that one too, the stricter winning, so the thread's repository's `dreamference.toml` counts (`ling_airgapped::resolve_in`). The conformance cases carry `"airgapped": "on"` for that level. Full Access is selectable at `off` in the picker, as in Codex; only `on` disables it. A `!` command's item (`source: "userShell"`) is drawn open with a `!` mark, and shown even when command output is hidden; Codex leaves these items out of `thread/read`, so they do not come back on reload.
- `ling-admin desktop {install,run,build,status}` needs **Node 22.13+ and npm only** (Forge 8's floor; and `dpkg` for the `.deb`, no `fakeroot`); `desktop run` packages the app and runs the packaged binary, never `electron-forge start`, whose dev server Work's `app://` page does not use.
- Night Shift recognises the `ling` bundled inside the app as an app-server by name and `app-server` in its command line, not only the installed binary (`NightShiftHost._is_app_server`).
- `DesktopInstaller`'s rustup helpers stay because the Codex build drives them.
- `DesktopRunner.has_source()` tells a checkout from a release install ([install-modes.md](install-modes.md)).

## Phase 2 (DESKTOP_PARITY §4.2)

- **The window's preferences** (`desktop/electron/src/prefs.ts`): one `prefs.json` under the data folder, mode 0600, every key and value checked against `desktop/ui/src/prefs.json`, the schema the page is built with (`prefs/read`, `prefs/write` over the one channel); a browser on `ling web` keeps the same keys in `localStorage`. Window settings only: agent settings stay in `~/.mightling/config.toml`, written by the server.
- **Opening a thread reads it** (`thread/read` with its turns); it is resumed only when a request needs it loaded (`loader.ts`: a turn started, steered or stopped, a compaction, a review, the goal or the queue changed), once, through `RpcClient.beforeRequest`, and a thread this window started, forked or resumed counts as loaded (`afterResponse`). A thread already loaded, or running (`status.type` active), is resumed on open so its events stream. Why: `thread/resume` writes to the rollout, and `thread/list`'s `updatedAt` is the rollout's modification time (codex's `thread_summary.rs`), so opening a thread made the sidebar call it active now. A Codex patch was not an option (the patches are at their size cap).
- **The keymap** is data (`desktop/ui/src/keymap.json`, §2.19 with a `built` or `planned` status per action); handlers name their action with `keyAction("<id>")` and `keymap.test.ts` holds the table and the code together. On macOS the table's `Ctrl` is ⌘ and `Super` is Control (`commandIsCtrl` in `keymap.ts`; Tab chords and the terminal context keep Control), for matching, recording (`chordOf`) and labels (`keyLabel`, `shortcutLabel`); `preview.ts` forwards ⌘ chords from a preview page as `Ctrl`.
- **The composer** (item 4): `composer.ts` (completion triggers, slash commands, prompt history, the approval keys), `turns.ts` (steer, queue, take back, fork over the RPC client), `ComposerView.tsx`. A Shift+dragged image is sent by its path, which the preload reads with `webUtils.getPathForFile` (`electronBridge.pathForFile`); `/airgapped default <level>` runs `ling airgapped default` in the main process (`work/airgapped-default`).
- **Window-side git** (item 6, `desktop/electron/src/git.ts`): `git` with an argument list (never a shell), `GIT_TERMINAL_PROMPT=0`, output capped at 16 MB; a repository is accepted only as its own top level, paths only inside it, a hunk patch only on stdin and only if its headers stay inside; `push` and the pull-request page are refused at `/airgapped on` (main.ts asks `ling airgapped --thread`). Nothing runs `git` at start-up, so the egress audit's app session sees none. The main process never reads a user's folder (a project, a repository, a worktree's source, an environment file) synchronously: `userfs.ts` goes through `fs.promises` with a 10 s limit, because on macOS the first access to a folder under ~/Documents, ~/Desktop or ~/Downloads waits on the access prompt, and `repositories()`'s synchronous walk froze the whole app there (1.7.0 Mac test); `userfs.test.ts` injects reads that never answer. A read that timed out still holds a libuv worker, and Node's teardown waits for it (the Mac's main process outlived SIGTERM, windowless): with any still pending (`pendingCalls`), `will-quit` and the SIGTERM fallback end the process with SIGKILL. `app.e2e.ts` holds a read of a FIFO nobody writes (`MIGHTLING_TEST_PENDING_READ`) and checks SIGTERM still ends the app. Synchronous calls remain only for the app's own files under `CODEX_HOME` and for PATH lookups. On macOS `/usr/bin/git` is run only when `xcode-select -p` names a developer folder with a git in it (`gitMissing`; every run of the stub pops the Command Line Tools dialog, in any folder): without one, `git()` refuses with a hint, `git/repos` answers no repository and the review pane shows the hint (`git/missing`); a `git` before the stub on PATH is used as it is. Editors: `editors.ts`. The review pane is `ReviewPane.tsx` over `diff.ts`; a generated commit message is an ephemeral, read-only thread (`turns.ts` `askOnce`).
- **Worktrees and hand-off** (item 7, `worktree.ts`): the `codex-worktree` crate's contract step for step from the main process (`$CODEX_HOME/worktrees/<4 hex>/<repo>`, detached, `core.worktree` in `config.worktree`, `codex-thread.json`), plus snapshots under `refs/mightling/snapshots/` before a removal or a hand-off, `.worktreeinclude`, and the hand-off itself. A removal is refused unless the checkout is one of the source's managed worktrees. Which thread works where is a window preference (`worktreeThreads`); later turns carry `cwd`. Settings › Worktrees writes `[desktop]` in `config.toml` through the server, the keys the crate reads.
- **Local environments and tasks** (item 7, `environments.ts`, `tasks.ts`): read from `.codex/` and `.mightling/`, written to `.mightling/` only (`smol-toml`); setup and actions run in the user's shell as bottom-panel tasks, each its own process group, refused at `/airgapped on`.
- **The shell** (item 2, `shell.ts`, `CommandMenu.tsx`, `SettingsDialog.tsx`): the page handles every shortcut from `keymap.json` with the user's overrides (`keyOverrides` in the window's preferences, applied as the page renders); the Electron menu only shows keys (`registerAccelerator: false`), so Ctrl+W never closes the window. Back/forward, undo/redo of archive and rename, CSS zoom for the text size.
- **Windows and panes** (`windows.ts`; pop-outs since item 3, several windows and detachable panes since 2026-10-22, DESKTOP_ELECTRON §13): every window on the one app-server; `WindowHub` tags each window's request ids (`<webContents id>␟<id>`), returns each answer to its window, broadcasts notifications and server requests, and answers a later window's `initialize` with the first one's result, before `server.ts` vets the message against the policy. **One composer per thread:** the first window to show a thread (a pop-out when it opens, or "Use the composer here") owns it; `COMPOSER_METHODS` (turn start/steer/interrupt, review, compact, revert, queue and goal changes) and answers to the thread's server requests are refused from any other window and from panes, and the page mirrors the thread read-only there (`composerOf`); the server's unasked requests are answered by one window (`answersFor`). The routing cases are `windows.vectors.json`, run with the policy by `windows.test.ts`, which also runs `ling web`'s conformance cases from every kind of window. **Panes** (`#pane=terminal|review&thread=<id>`): the header button or the Window menu detaches, closing the pane's window docks it back; a pane asks the window it came from for what needs the composer or its permissions (`pane/relay`, `paneAction`). **Terminals across windows** (`terminal-mirror.ts`): the starting window publishes each tab and its exit (the server answers an exit only to it), every window gets the list, and the main process keeps each tab's last 256 KB of output, which a window drawing a tab it did not start reads first (`TerminalHub`'s `seed`). Only the app's windows may use the channel (`windowFor`). Links: `ling://` and the older `mightling://` (`app.json` `scheme`, `legacySchemes`).
- **Terminal tabs** (item 8, `terminal.ts`, `TerminalView.tsx`): xterm.js over `command/exec` with `tty` under the composer's permission profile; the hub routes `command/exec/outputDelta` by `processId` and keeps what arrives before a tab is drawn. The `!` command (`thread/shellCommand`) is the other way to run one; it runs unsandboxed and is refused at `/airgapped on`.
- **Held work** (2026-10-17, landed 2026-10-18 as 1d9eb48): what needed new methods in `policy.json` waited on `desktop/p2-held` for `cargo test --release -p ling-launcher -p ling-web-server` in the export with its `ling-rs/`; a policy change lands only after that run.
- **Settings › Node** (`nodes.ts`, 1.7.1): `ling node list --json` and `ling node use <name>` run by the main process (`node/list`, `node/use`), like `work/airgapped`: launcher commands, not app-server methods, so `policy.json` is unchanged. Only a choice the last list offered is sent, never an address; nothing browses until the page opens (an mDNS query in the audit's app session would be a finding). `app/relaunch` restarts the app so its app-server resolves the new node. NODE §6.3.
- **Methods still to add** to `policy.json` are listed, with their item, in `tests/test_desktop_parity.py` (`POLICY_TO_ADD`); adding one needs the Rust conformance run, so it never lands while a SWE-bench night owns the machine.

## Phase 3 (DESKTOP_PARITY §4.3)

- **The tab area** (`TabArea.tsx`, `tabs.ts`): Review and file tabs in one strip, every tab kept mounted (the ones behind hidden); Ctrl+W closes the tab in front and Ctrl+Shift+T reopens it. **File tabs and the file tree** (item 1, `FileTree.tsx`, `FileView.tsx`, `files.ts`): read only, through the server's `fs/readDirectory|readFile|watch|unwatch` (the policy refuses `fs/writeFile` and `fs/remove`); open folders and open files are followed with `fs/watch`; highlight.js core with twenty bundled languages; a file over 4 MB asks before it is read (`file/size`, a stat in the main process; a browser on `ling web` has no such guard). **Search files and go to line** (item 2, `FileSearch.tsx`): Ctrl+P over the allowed v1 `fuzzyFileSearch` in the thread's folder, `name:line` opens at a line; Ctrl+L with a file tab in front is the same dialog started at `:`. **The artifacts viewer** (item 3, `ArtifactView.tsx`, `artifacts.ts`): Markdown (`renderDocument`: images and links kept as references, a local image read through the server, a local link opened in a tab), images, PDFs drawn by pdf.js 4.10.38 (Apache-2.0, loaded only when a PDF opens, `isEvalSupported: false`) and HTML sanitised into a shadow root (no script, frame, form, handler or navigation; `sanitizeDocument`), all inside the unchanged CSP (still no `frame-src`); a Source switch; LaTeX shows its source only (no `tectonic`). What a finished turn created opens by itself unless Settings › General says not to (`openArtifacts`).
- **The preview tab** (item 4, `preview.ts`, `preview-rules.ts`, `PreviewTab.tsx`): a `WebContentsView` laid over the tab's body (the page reports where, scaled by `currentCSSZoom` because the text size is CSS zoom, and hides it under any dialog), on its own session `persist:mightling-preview`: no preload, sandboxed, no permission granted, no pop-up window, every request and navigation decided by `decide()` before it connects. Loopback, LAN names and addresses and files load; an internet site asks (Allow once, Always allow, Block; Settings › Browser keeps `previewSites`); `/airgapped on` (the thread's, through `ling airgapped --thread`) keeps it to loopback and files. A download always opens a save dialog and is refused from a site that may not load. Comment mode runs `PICK_SCRIPT` in an isolated world (1307) and sends the element and the comment to the composer. Developer tools only with Settings › Browser › Developer mode, for tabs opened after. Shortcuts pressed inside the page reach the tab through `before-input-event`. `ling-admin audit egress --app` opens a preview of its own loopback page (`dreamference/audit/preview_page.py`, `MIGHTLING_APP_AUDIT_PREVIEW`) that reaches for the internet by picture, script, stylesheet, `fetch`, link, preconnect and DNS-prefetch hints; the session passes only if none of it connects or asks a resolver, and fails as a trace if the page never ran. It found that Blink resolves `<link rel="dns-prefetch">` names straight from the renderer, past every request rule, so the app starts with `--blink-settings=dnsPrefetchingEnabled=false` (`egress.ts`), and preview responses carry `X-DNS-Prefetch-Control: off`. On macOS only it also starts with `--use-mock-keychain` (`platformSwitches` in `egress.ts`): os_crypt's "Mightling Safe Storage" keychain lookup prompted on every ad-hoc-signed build and hung an `open` in SecItemCopyMatching (1.7.0 Mac test). The app uses no `safeStorage` and keeps no secret; the preview session's cookies are what is then stored with a fixed key. Revisit with a Developer ID. A Playwright page screenshot does not hold the view: `phase3.e2e.ts` draws it in (device pixels: the views' bounds are in DIP).
- **The Activity view** (item 5, `activity.ts`, `ActivityView.tsx`, Ctrl+Alt+U): the 20 most recent threads' last 12 turns through `thread/turns/list` (full items), commands, file changes, tool calls, web searches and subagents, newest first by day, filtered by kind and project; a row opens its thread. Nothing is recorded for it.
- **Ask's files** (DESKTOP_PARITY_CLAUDE §4.1): the tab list is one, and `viewTabs` (`ask.ts`) gives each view its part: Ask the file tabs inside the shown question's folder, Work everything but files under the Ask root. `MadeFile` (App.tsx) is the card for a file an Ask answer added; the tree and Ctrl+Shift+E use the question's folder (`askTree`, apart from Work's `treeShown`). `e2e/extras.e2e.ts`; the stand-in writes `report.md` when a question says "with a report".
- **Links in answers** (DESKTOP_PARITY_CLAUDE §4.5): `webLink` (markdown.ts) makes an http(s) address with a host and no credentials a `.web-link` span; the page's click handler reads the thread's level then and opens `LinkDialog`; the app's main process opens it with `shell.openExternal` (`open/url`) after `webUrl` (links.ts) and `offline()`; `ling web` uses `window.open` with `noopener,noreferrer`. `e2e/links.e2e.ts` replaces `shell.openExternal` with a recorder.

## Tests

- `npm test` in `desktop/electron` (vitest, the main-process modules; `policy.test.ts` runs `ling web`'s conformance cases; `ask.test.ts` runs an Ask thread through `AppServer` against a scripted `ling`) and in `desktop/ui`.
