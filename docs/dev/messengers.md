# Phone messengers: `ling signal`, `ling chat`, `ling-admin matrix`

Specs: `specs/DREAMFERENCE_MIGHTLING_SIGNAL.md` (§16–§17) and `specs/DREAMFERENCE_MIGHTLING_CHAT.md` (§14–§15) record what was built and verified. The user page is `docs/messengers.md`.

**Phone messengers ship with Mightling and are off until a command turns one on** (specs `specs/DREAMFERENCE_MIGHTLING_SIGNAL.md` §16 and `specs/DREAMFERENCE_MIGHTLING_CHAT.md` §14 record what was built; user page `docs/messengers.md`). There is one command surface, `ling`: `ling signal …` and `ling chat …` are launcher subcommands like `ling web`, and the only `ling-admin` part is `ling-admin matrix …`, because containers are `ling-admin`'s. Every bridge is a client of `ling web`, so a message becomes an Ask thread under the same bridge policy, and each is its own process, because it needs the network and `ling web` promises it calls nothing on any network. Nothing is started, listens or registers until `ling signal setup`, `ling chat start` (after `ling chat telegram setup` or `ling-admin matrix start`) or `ling-admin matrix start`; their `stop` commands *disable* the unit, so off survives a reboot; and `ling-admin audit egress` names each one that is on as a declared exception (`EgressAudit.declared_exceptions`: the system unit `mightling-signal.service`, the user unit `mightling-chat.service` with a Telegram token, the user socket `mightling-matrix-proxy.socket`), never passing it silently. Five things to keep:
- **Signal is linked to the owner's own account and reads Note to Self alone** (crate `ling-rs/signal/`, `ling-signal`). The launcher links the crate for `ling signal …` (`ling-rs/src/signal.rs`, Linux only); the crate also builds a **small `ling-signal` binary**, the daemon the system account `mightling-signal` runs from `/usr/local/lib/mightling` (users' homes are 0750, and the 300 MB `ling` with its home folder and rename migration is the wrong thing to run as a system account). It is built in the same Cargo run as `ling` (`BUILDS_SIGNAL` in the builder), shipped as the optional release asset `ling-signal-<target>.gz`, installed beside `ling` and **never linked onto PATH**; `ling signal setup` copies it for the account and `ling signal setup --refresh` copies it again after `ling update`. The bridge's own commands (`serve`, `init`, `retool`, `pair`, `bind`, `trust-owner`) are accepted only from that binary.
- **Several Signal accounts, one bridge each** (spec §18, branch `signal/multi-account`): `ling signal setup --name NAME` adds an *instance* with its own system account `mightling-signal-NAME`, state `/var/lib/mightling-signal-NAME`, template unit `mightling-signal@NAME.service` and `ling web` device `signal-NAME`; the first stays `default` with today's names, byte for byte (`unit.rs` pins its unit). At most four, 2 GB to spare above their caps; one Signal account, one instance; for now every instance on a node serves one Linux user (§18.8). Host reads go through `cli::Host`, so the tests use a scratch root and never see the live bridge.
- **signal-cli and Java are fetched by setup, pinned by URL and SHA-256, never bundled**: signal-cli 0.14.9, libsignal's arm64 JNI build 0.103.0 (signal-cli ships x86_64 only) and Eclipse Temurin's JRE 25.0.4.1+1, each checked as the user before it is unpacked as root under `/opt/mightling` (`ling-rs/signal/src/setup.rs`), the way `ling-admin docs setup` fetches ling-docs's runtime. No apt package for Java: a pool URL vanishes when a security update supersedes it.
- **`ling chat` is one bridge with two adapters** (crate `ling-rs/chat/`, `ling-chat`, linked into `ling`): **Matrix**, private, against the user's own tuwunel homeserver (`dreamference/chat/matrix_homeserver.py`, image pinned by digest) on an **internal Docker network** with no route out, reached by the host through `systemd-socket-proxyd` user units on `127.0.0.1:6167` and by the phone through `tailscale serve`; and **Telegram**, less private, by long polling, with consent typed at a terminal. The tailnet name becomes the Matrix server name, which is permanent: `start` refuses when Tailscale reports another. The hub signs in to `ling web` as `ling web ask` does, so a restarted `ling web` just means signing in again.
- **Telegram's Mini App** (TELEGRAM_MOONSHOT §15): with `[chat] telegram_mini_app_url` set, the bridge makes each paired user's menu button (and `/app`) open `ling web` over the user's own HTTPS front, which the phone loads directly, never through Telegram. `ling web` serves that name (`Config::public_names`), keeps the device credential as the only way in, and `bridge.js` connects only after `POST /api/telegram/check` confirms the launch was signed by this node's bot for a paired user (`telegram_app.rs`). Framing stays denied, so web.telegram.org cannot host it.
- **The air gap**: Signal acts only at `/airgapped off` (read through `ling web`'s `/api/airgapped`, since the system account cannot read the user's config) and Telegram pauses at `on`; Matrix, which never leaves the machine, keeps working.
- **Tests**: `cargo test --release -p ling-signal -p ling-chat` in the scratch export (the release job does the same), against a scripted signal-cli, a stand-in `ling web`, Bot API and homeserver, plus one test through the real `ling-web-server`; the Python side's only ways out are `MatrixHomeserver._run` and `_http`, both replaced in its tests. Signal has run against a real account once: on 2026-10-12 the owner set up the published 1.6.0 in linked mode on gx10-1a2b and asked a question in Note to Self, answered there, then `/stop` (spec §17.2; dedicated-number mode, approvals from the phone and attachments are still unexercised). From 1.6.1 Signal is no longer labelled a preview. While a SWE-bench run holds the model gate, a Signal question is refused, never let through: the bridge recognises the gate's 503 text in the failed turn and tells the owner the run and its time left (spec §17.3). Nothing has run against real Telegram, Matrix or Tailscale, and those two keep the preview label.
- **Images (2026-10-20, Signal spec §19.1, chat spec §16.1):** every bridge passes images and files on through `ling web`'s `/api/upload?read=1`, which reads an image's text with Tesseract (`ling-rs/web/src/ocr.rs`; capped, offline) and reports whether the served model takes images (the catalog's `input_modalities`, written by the launcher from SGLang's `/model_info`). The bridges' pure `compose` builds the turn (`[Screenshot text: …]`, `localImage` when the model takes images) and never sends an empty one: with nothing usable the bridge answers itself. Signal now downloads attachments (signal-cli cannot fetch one later) and deletes every one that is not the owner's as it arrives.
- **A new thread after a silence (Signal spec §19.2, chat spec §16.2):** `[chat] new_thread_after_hours` (default 4, 0 off) in the user's config; `ling web` serves the `[chat]` settings at `/api/chat/settings` (`chat_settings.rs`) for the Signal bridge, `ling chat` reads them itself, both every minute.
- **Bounds and the phone prompt (Signal spec §19.3, chat spec §16.3):** `[chat] answer_seconds` (180), `tool_calls` (25), `command_seconds` (60): steer "answer now", interrupt 30 s later, one final turn without tools (90 s). `limits.rs` is the same in both crates from `Verdict` on (`tests/test_chat_limits.py`). Threads start with the `chat` prompt (`ling-rs/prompts/chat.md`) in `ask/chat-<hex>`, which is how the gate's extension tells a phone's thread.
- **Quick follow-ups (Signal spec §19.4, chat spec §16.4):** a message during an answer is added to the question while it opens or uploads and steered in (`turn/steer`) while it runs; refused or not joinable, it waits, and what waited is one question.
- **Telegram Phase 1 (MOONSHOT §14):** a topic is the hub key `telegram:<chat>/<topic>` (`hub::topic_of`, `telegram::target`); with topics on, a message sent in the main chat (outside any topic) continues the topic most recently used in that chat (`last_topic` in `threads.json`, updated on user messages and bot answers), while `/new`, the first message ever, or a deleted or closed last topic (`TOPIC_DELETED`, `"message thread not found"`) opens a fresh topic and remembers it. `blocks.rs` builds rich-message blocks from the model's Markdown and never passes markup through; approvals carry random nonces (`a:<nonce>:<choice>`) and close to a disabled button; every bridge keeps a stopped or cut-off answer as a message. Phase 0's checklist for a throwaway bot is MOONSHOT §14.1.
- **Voice (Signal spec §19.5, chat spec §16.6):** recordings go to `/api/transcribe` (speaches on the node), never uploaded; "Heard: …" first, a failure said.
- **Files back (Signal spec §19.6, chat spec §16.7):** `ling web`'s `/api/ask/files` and `/api/ask/file` (`ask_files.rs`; the thread's folder only, no links, refused at `/airgapped on`); the bridges offer a file the answer names as their own approval and send it only on yes.
- **Night Shift from the phone (Signal spec §19.7, chat spec §16.8):** `ling web`'s `/api/night/repos|add|status|reports` (`night_phone.rs`, `ling night add` run in the chosen checkout); the bridges confirm before queueing and push each new morning report once.

- **Speed and feedback (Signal spec §19.8, 2026-10-26):** answers stream into one message by edits (typing until the first words in dedicated mode; a "Working on it…" status line at once in Note to Self, which shows no typing), at most nine edits a message, every 3 s, the whole answer last; a failed edit sends the answer whole. The journal gets two timing lines per question (ids and durations only: Signal's server times, first shown, turn started, first output, turn ended, acked, end to end). A phone's thread (`chat`) runs without `image_search` (`promptThreadConfig` in `ling-rs/web/policy.json`, applied on start and resume), and the phone prompt searches only when the answer needs it and runs shell commands with `exec_command`, never through Code Mode's `exec` (which stays: the catalog's `tool_mode`, not `features.code_mode`, gives it). Since 2026-10-27 a phone's thread also runs with `approval_policy = "never"` (same `promptThreadConfig`): a weather question once asked the owner over Signal to approve an escalated `curl` the sandbox would have run anyway (its network is on unless `/airgapped on`), cued by stale `curl` prefix rules in `$CODEX_HOME/rules/default.rules` that Codex lists under on-request; at `never` that list and the escalation section leave the prompt, and an escalation is refused at once and rerun sandboxed. The phone prompt sends dated facts to `ling-search --read` first and keeps `curl` for what it cannot read.
- **No clarifying questions or guessed attachments on the phone (2026-10-27):** `ling-rs/prompts/chat.md` tells the agent never to ask a clarifying question on the phone (take the most likely reading, typos included, state it in one short line at the start such as `"Taking this as Unix."`, and answer fully), to ask only before something destructive or costly (push, merge, delete, sending outside the chat, long jobs) as one short question at the end of the answer (a phone thread runs at `approval_policy = "never"`, so an escalation cannot ask), and never to mention attachments, images or files unless the message carries one (marked by the bridge with `[Screenshot text: …]`, `[Attached and saved in this thread's folder: …]` or an attached image).
